
# Package-editing UI

The implementation is very janky.

There are cases elsewhere in DovahKit where we have multiple `QAbstractItemModel`s that offer views into different sections of a hierarchy of heterogenous[^heterogenous] node types. Quest dialogue is a major example, where we have a hierarchy of branches, which contain topics, which contain infos -- two different branch-node types and one leaf-node type. This is one of[^datastores-for-shared] the situations where DovahKit uses what I call a "datastore:" a `QObject` that stores data in a dedicated format, to be shared by multiple `QAbstractItemModel`s.

I should've used a datastore for packages. I did not. The package UI uses two models: `PackageDataModel` and `PackageProcedureTreeModel`. An instance of the latter stores a `QPointer` to an instance of the former, and uses that to display packdata appropriately when packdata is referenced by a procedure tree node. This means that a large amount of logic for managing changes to packages is shoved into the code for the dialog UI.



[^heterogenous]: Theoretically, a `QAbstractItemModel` is capable of storing a tree of heterogenous 2D grids: every grid cell can have a child grid of an arbitrary size, and every cell can possess an arbitrary set of data. However, there are two issues with actually using `QAbstractItemModel`s to represent trees of heterogenous node types with multiple views pointed at different parts of the model. The first is that row and column headings are *not* capable of being heterogenous; one set of row and column headings is defined across the entire model. This means that, for example, if you were to construct a single `QAbstractItemModel` that had dialogue branches (`DLBR`) as the top-level nodes, dialogue topics (`DIAL`) as child nodes, and dialogue infos (`INFO`) as grandchild nodes, you'd run into the problem that a tableview of branches, a tableview of topics in some selected branch, and a tableview of infos in some selected topic would all be forced to have the same column headings.
  
  The larger issue is that QAbstractItemModel relies heavily on type erasure by way of `QModelIndex` and (through the `data()` and `setData()` functions) `QVariant`. All access to the contents of the model relies on `QModelIndex` to specify nodes, and `Qt::ItemDataRole` to specify data within a node. This means that, for example, overrides of functions like `QAbstractItemModel::moveRows` are also type-erased: all model operations require you to undo the type erasure and then perform type checking at run-time. This is... burdensome... to say the least, and it makes for very messy code.
  
  Datastores solve both of these problems, by way of strongly-typed accessors and internals. A custom `QAbstractItemModel` subclass can be designed to wrap the datastore and access data of the specific type that is of interest to it, supplying the appropriate headings for its level of hierarchy, and only having to deal with (and type-erase) one node type at a time.

[^datastores-for-shared]: The other major use case of datastores is situations where a `QAbstractItemModel` deals with homogenous node types but there are many instances of that model, or many instances of the nodes. For example, the `DKFormPicker` widget acts as a drop-down to choose forms from, listing their editor IDs. There can be several formpickers in the UI at a time, each of which may list dozens or hundreds of forms. If each formpicker had a wholly independent model, each one walking the lists of all loaded forms and converting editor IDs from `std::string` to `QString`, the resulting lag would be immense. Instead, we have a datastore singleton for formpickers which generates the nodes one time and is principally responsible for maintaining those nodes as forms change. Each formpicker's model will load nodes from the datastore and sort them asynchronously (they have a per-tick time budget of 33ms), storing node pointers and using custom signals emitted by the datastore for synchronization.
