
= SCOPED ENUMS AND WHAT WE'RE DOING ABOUT THEM =

In C++, you have a few options for enumerations, but they're all terrible and they 
suck. Obviously we need some sort of solution, so read through for all the angles 
I've covered or just scroll to the bottom to see what we're going with for this 
project.


== Normal enumerations ==

Consider an enumeration like this:

   enum Flags : uint8_t {
      use_widget,
      use_gadget,
      use_device,
   };

This enumeration can be implicitly casted to an integer, which is exactly what we 
want for flags. It can also be used as a typename and be given a specific underlying 
type. However, this enumeration pollutes the global namespace: (use_widget) is now a 
token in the global scope. Moreover, enumeration values can conflict -- not just in 
definition, but in usage. Once you define the enum above, you aren't even allowed to 
define an enumeration in the same scope that contains its own (use_widget) value even 
if you always qualify the values with the prefixes.

This in turn means that you can't easily use namespaces to hack your way around the 
scope pollution, e.g. something like this:

   namespace _scoped_enums {
      enum Flags : uint8_t {
         use_widget,
         use_gadget,
         use_device,
      };
   }
   using Flags = _scoped_enums::Flags;

Although we're no longer polluting the global scope, we're still polluting the throw-
away scope that we've created for the enum. This means that we can't put another enum 
in that scope if its values have the same enum, i.e. using the above along with the 
below is a parse error:

   namespace _scoped_enums {
      enum Flags2 : uint8_t {
         use_machine,
         use_computer,
         use_device,
      };
   }
   using Flags2 = _scoped_enums::Flags2;

Because these enums have values with the same names in the same scope, the program 
won't compile, even though we will never actually refer to any of those values without 
also qualifying them with the name of the enum (via the using declarations). This 
literally shouldn't even be an issue. If enums were designed even a little bit sensibly, 
the language would only consider ambiguous references to enum values an error, as 
opposed to choking to death the second it sees two same-named values from different 
enums in the same containing scope.


== Enum classes ==

The "solution" to this is to use an enum class:

   enum class Flags : uint8_t {
      use_widget,
      use_gadget,
      use_device,
   };

And that works great until you try to do anything that relies on enums implicitly 
casting to integer, which is disabled for enum classes:

   Flags myFlags = Flags::use_widget | Flags::use_gadget;
   //
   uint8_t flagsObtainedFromSomewhereElse;
   Flags   otherFlags = flagsObtainedFromSomewhereElse;

You *can* *ex*plicitly cast these enums to and from integers:

   Flags myFlags = (Flags)flagsObtainedFromSomewhereElse;

   enum class Foo {
      zero
      one,
      two,
      three
   };
   Foo  bar = Foo::zero;
   auto baz = myArray[(int)myFoo];

But surely there must be a better way, right? Surely, the language wouldn't force 
you to deal with this kind of thing just to avoid polluting namespaces and dealing 
with naming collisions that literally shouldn't even be an issue.

This language doesn't have a way to scope an enum while still retaining the ability 
to implicitly cast it. The construction (enum struct) has explicitly been defined by 
the standard to be the exact same as (enum class), intentionally locking out the 
possibility of using it for implicitly-castable scoped enums in a future version of 
the language, which is an... incredible... decision.


== Struct wrappers ==

You can also use a struct to wrap an unnamed, un-scoped enum:

   struct Flags {
      enum : uint8_t {
         use_widget,
         use_gadget,
         use_device,
      };
   };

The struct's namespace is "polluted" by the unscoped enum, rather than the global 
namespace; the struct effectively *is* the name of the enum, allowing you to refer 
to the enum's values by qualifying them with the name of the struct. However, you 
can no longer use the enum's name as the type of a variable or member. While that is 
less of an issue for bitmasks and whatnot, it's more of an issue for things that are 
*actual enums* but that should still be intuitively usable as array indices and so 
on.

You could potentially work around that by defining the struct itself as a wrapper 
for the enum's underlying type, giving it all the operators and other boilerplate 
needed. A decent compiler will optimize out all such access, such that the struct 
effectively "is" the underlying integral type. However, after multiple attempts, 
I was unable to get this to play nice with the *full* set of C++ features under 
MSVC 2019, e.g. constexpr definitions and so on. Apparently, the following

   constexpr cobb::int_wrapper<int> test = 5;

is somehow not a constant expression. Moreover, you can't subclass these damn 
things and still keep *all* of the constructors and conversions and whatnot (yes, 
I tried using a using declaration on the constructor), which means that if you try 
to go this route, you have to include all of the relevant boilerplate *in each 
enum.* Copying and pasting twenty operators into every enum is obviously not a 
tenable solution.


== Prefixed enum value names ==

Like so:

   enum Flags : uint8_t {
      kFlags_UseWidget,
      kFlags_UseGadget,
      kFlags_UseDevice,
   };

This is ugly and the compiler whines at me whenever I do it -- being sure to 
recommend (enum class) to me every time, as if I haven't considered that and 
consciously ruled it out.


== Preprocessor macros wrapping an enum ==

Yeah. This is big brain time.

Let's start with these:

   #define SCOPED_ENUM(name, ...) namespace _scoped_enums { namespace UNIQUE_##name { enum name { __VA_ARGS__ }; }; }; typedef _scoped_enums::UNIQUE_##name##::##name name;
   #define TYPED_SCOPED_ENUM(name, type, ...) namespace _scoped_enums { namespace UNIQUE_##name : type { enum name { __VA_ARGS__ }; }; }; typedef _scoped_enums::UNIQUE_##name##::##name name;

   SCOPED_ENUM(Foo,
      a = 5,
      b = 3,
   );

So the obvious problem to start with is that our enums no longer actually look 
like enums. Is that picky? Sure. But this whole thing shouldn't even be an issue, 
so  whatever solution we pick to address it shouldn't be unacceptably hideous.

Maybe we can do a bit better with these? We can use __COUNTER__ to guarantee a 
unique namespace name, and we can jam the entire enum definition into the macro:

   #define _SCOPE_ENUM_HELPER(x, y) x ## y
   #define SCOPE_ENUM(c, ...) namespace _SCOPE_ENUM_HELPER(_scoped_enums, c) { __VA_ARGS__##; }; using namespace _SCOPE_ENUM_HELPER(_scoped_enums, c);

   SCOPE_ENUM(__COUNTER__, enum Baz : int {
      a = 5,
      b = 3,
   });

Next, let's abstract away the counter argument:

   #define _SCOPE_ENUM_HELPER_01(x, y) x ## y
   #define _SCOPE_ENUM_HELPER_02(c, ...) namespace _SCOPE_ENUM_HELPER_01(_scoped_enums, c) { __VA_ARGS__##; }; using namespace _SCOPE_ENUM_HELPER_01(_scoped_enums, c);
   #define SCOPE_ENUM(...) _SCOPE_ENUM_HELPER_02(__COUNTER__, __VA_ARGS__)

   SCOPE_ENUM(enum Baz : int {
      a = 5,
      b = 3,
   });

But we have a problem: if we import the namespace, then we also import its pollution; 
our sample enum values, (a) and (b), end up in the global namespace. We can avoid 
that if we specify the name of the enum redundantly:

   #define _SCOPE_ENUM_HELPER_01(x, y) x ## y
   #define _SCOPE_ENUM_HELPER_02(x, y, z) x ## y ## z
   #define _SCOPE_ENUM_HELPER_03(name, c, ...) namespace _SCOPE_ENUM_HELPER_01(_scoped_enums, c) { __VA_ARGS__##; }; using _SCOPE_ENUM_HELPER_02(_scoped_enums, c, ::##name);
   #define SCOPE_ENUM(name, ...) _SCOPE_ENUM_HELPER_03(name, __COUNTER__, __VA_ARGS__)

   SCOPE_ENUM(Baz, enum Baz : int {
      a = 5,
      b = 3,
   });

But that's obnoxious.

There's also another hidden issue waiting to bite us: we can't use single-line 
comments within the enum definition. Macro invocations get collapsed into one line, 
because this programming language is ancient. That means that we can't do this:

   SCOPE_ENUM(Flags, enum Flags : int {
      master = 0x0001,
      localized_string_table = 0x0080,
      light = 0x0200, // SSE only
   });

The above parses as this:

   SCOPE_ENUM(Flags, enum Flags : int { master = 0x0001, localized_string_table = 0x0080, light = 0x0200, // SSE only });

That's an unterminated enum and containing namespace -- obviously wrong. We need to 
use block comments instead, which is also obnoxious.

Further tests with this indicate that semicolons and single-line comment tokens can 
cause MSVC's preprocessor to choke and die even if they occur inside of a block 
comment. IntelliSense also regularly throws up all over the floor upon encountering 
any large or large-ish enum using these macros: even after carefully pruning an 
enum to remove anything that might make the preprocessor choke, IntelliSense often 
still thinks that *something* is causing the macro invocation to fail to terminate 
properly, and it fails to show the macro's substituted content properly when you 
hover over it for a tooltip. (The code still compiles; this is purely an issue in 
IntelliSense.) This has not been helped by following Visual Studio's suggestion to 
put the macros in a "hint" file.


== Namespaces but we just tack a random number on every time we get an error ==

Like so:

   namespace _scoped_enums {
      enum Flags : uint8_t {
         use_widget,
         use_gadget,
         use_device,
      };
   }
   using Flags = _scoped_enums::Flags;

   namespace _scoped_enums_1234215 {
      enum Flags2 : uint8_t {
         use_machine,
         use_computer,
         use_device,
      };
   }
   using Flags2 = _scoped_enums_1234215::Flags2;

I hate this.


== THE CHOSEN APPROACH ==

We went with the preprocessor macro; it's the least hideous approach.
