
If you've read the documentation on how the game loads forms, then you now know 
that GMST records don't actually define  forms. Game settings are not forms and 
do not have form IDs,  which means  that as long as their special-case  loading 
code is  reached, they will load regardles s of their form ID. This  means that 
game settings disobey the usual rules for form IDs in the following manner:

 - Multiple GMSTs can share the same form ID.

 - GMSTs can share their form IDs with real forms,  so long as those forms load 
   later than the GMSTs.

 - GMSTs can have form  IDs that are out of bounds or  otherwise invalid, as is 
   seen with a particular GMST record in Skyrim.esm.

 - If a file  contains multiple  GMST records with  different form  IDs but the 
   same editor ID, then one will override the other.

Only one such anomalous GMST record is known to exist in official content,  and 
official editing tools have never been  observed to break these rules after the 
game's initial release.  The information above comes  from disassembling Skyrim 
Classic. Additional  information comes from disassembling the  game and running 
tests in the Creation Kit:

 - A GMST record will only be recognized if EDID is the first subrecord inside.

 - Nameless GMSTs are  not retained when  resaving a file in  the Creation Kit, 
   and presumably, they aren't retained in memory at all.

 - Unrecognized GMSTs are  retained when  resaving a file  in the Creation Kit, 
   and they can even be seen in the Creation Kit's UI.
   
 - When multiple  instances of the same  game setting are loaded  (whether from 
   different files or the same file), the Creation Kit retains the last form ID 
   that it saw for that setting.

This has a number of  implications for loading and  managing GMSTs in DovahKit:

 - We cannot use form stubs to encode a GMST, because we can only have one form 
   stub per form ID,  and every form stub  must have a form ID.  Multiple GMSTs 
   can share  the same form ID,  and GMST records can load  even if their local 
   form IDs are impossible to convert into global form IDs. However, we do need 
   to generate form stubs for any loaded  GMST with a valid form ID, so that we 
   can  enforce constraints regarding  form ID sharing and overrides that  have 
   mismatched form types.

 - GMSTs must be indexed by name.

 - GMSTs must therefore be loaded differently than form stubs, and they must be 
   stored separately  from them. In practice,  this must be  done when DovahKit 
   initially parses an ES[LPM] file, which means that GMSTs cannot be loaded on-
   demand but rather must be loaded immediately and in full.

 - String GMSTs encode their values as localizable strings. Those normally only 
   appear inside  of form data  that is loaded  on-demand, and so are  normally 
   only accessed after all localization files have been loaded. DovahKit's load 
   process must therefore take an extra step after localization files have been 
   loaded: it must loop  over all loaded GMSTs and pull  the appropriate string 
   content for GMSTs that rely on the localization files.

There are additional concerns that must  be addressed: to what extent should we 
support,  retain, and preserve anomalous GMST records? In the  vast majority of 
cases, these anomalies are quirks arising from the fact that the file format is 
not, in this case, suited to the data it  is being used to represent: GMSTs are 
not forms, yet are being encoded in a format that requires form IDs, instead of 
some special-case format. This means that  the vast majority of anomalous cases 
are file  format details rather than  quirks within the data itself.  Referring 
back to <basics.txt>, we see that like the Creation Kit, DovahKit aims to focus 
on the data  being represented rather than  on the representation itself,  this 
being a contrast to tools like xEdit. It wouldn't make sense to design the vast 
majority of DovahKit to be data-oriented only to then make this one thing file-
oriented. Accordingly, GMST anomalies are to be handled as follows:

 - GMSTs with no editor ID, a blank editor ID, or an out-of-place editor ID are 
   to be skipped, with a warning.

 - GMSTs with an unrecognized editor ID will be retained and re-saved.

 - GMSTs are not permitted to share their  form IDs with other forms. Where the 
   game  enforces this as a one-way  constraint (applying only if  the form was 
   loaded first), DovahKit enforces it bidirectionally in order to avoid horrid 
   complications with multi-threaded loading.

 - GMSTs can still have out-of-bounds or otherwise invalid form IDs.

 - If a GMST has a valid form ID, then  it will be re-saved with that same form 
   ID.

 - If a file  contains redundant GMST  records (i.e. multiple  records defining 
   the same setting, possibly with different form IDs), then DovahKit will only 
   re-save one record,  using the last loaded value (if unedited)  and form ID.

 - DovahKit will support allowing multiple game settings to share the same form 
   ID. This could  be potentially useful  for reducing form ID  usage, and with 
   the current implementation of GMSTs it costs us nothing.
