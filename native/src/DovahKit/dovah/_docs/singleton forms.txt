
In Skyrim,  some form types describe  "singleton forms." As  the name suggests, 
the game will never  create more than one instance of  these forms. If multiple 
records of this form type exist (whether  in a single file or across the entire 
load order), then they will all be  treated as overrides of the same form, even 
if their form IDs  differ. The final forms in memory will  use the form ID from 
the last loaded definition.

This behavior is implemented as a special case in the game's form loader (refer 
to <how the game loads forms.txt>).  The form types that act  as singletons are 
DOBJ and NAVI: the default object manager and the navmesh info map.

This begs the question: how should DovahKit handle singleton forms?

We need to create one form stub for  each form ID used by a record that defines 
a singleton form,  so that we can handle type-mismatched  overrides safely, and 
so that we know that  these form IDs  are unavailable  for record injection. We 
also want to rely on the form stubs for managing use info, which means that the 
content of singleton forms  needs to be loaded and  managed the same as for any 
ordinary form type.  That, of course, gives rise to a  complicated problem: how 
do we  manage on-demand  loading of a singleton  form's content, when  the form 
needs to be coalesced not just across multiple files, but through multiple form 
stubs?

One basic approach would be to co-opt  use info, to allow the stubs for a given 
singleton form to be aware of each other. An alternate approach would be to use 
the (file_load_order) to coordinate these stubs: when it loads a new stub for a 
singleton form, it  can iterate over all pre-existing stubs  for that singleton 
and copy their file data into the new stub, so that it can access the file data 
for the other records despite those records having had a different form ID. The 
two approaches are  more or less equal; neither is really any  cleaner than the 
other. The former approach keeps the  (form_stub) file list system "clean," but 
dirties up the  use info system and the code for loading form data.  The latter 
approach does the opposite, but requires  additional measures to identify which 
(form_stub) should be used to load a singleton form.

Each approach needs the following accommodations.


== Making singleton forms' stubs aware of each other ==========================

In order to load the data for a singleton form, we need to sort all source file 
information, to be sure that we pass  records into the form loader in the right 
order. Simply  sorting by file isn't enough, since a file could  hypothetically 
define redundant  records for the singleton form; as such, we  need to sort the 
source file entries by  their load order position and  their offset. Additional 
complications  arise during  sorting if  one of the  stubs has  been flagged as 
"edited."

I had tried writing  out code for  sorting, but it felt...  fragile. Sort these 
stubs by load order position and file  offset, unless they're both edited or in 
the active file, in which case, sort them by GRUP order or form ID? It felt too 
indirect, like it was creating room for edge-cases I couldn't readily see. Once 
I thought of the other approach,  and the ways it could simplify things, I went 
with it instead of trying to fully reason out this approach's complications.


== Copying source file information between stubs ==============================

Because we're  managing form stubs' source  file information as  we insert each 
individual  stub, we don't  need to take care of  sorting or any  other similar 
process. As long as  DOBJs aren't misplaced into other GRUPs,  we should always 
load them in  a predictable order.  If they are misplaced,  or if multiple DOBJ 
GRUPs  exist, then  the process of  merging source  file lists may  not produce 
consistent results between sessions because  we multi-thread file loading; that 
said, it's not our responsibility to perfectly handle every possible way that a 
file can be malformed.

In order to load the data for a singleton  form, we need to be able to identify 
which form stub was the last to load.  Fortunately, this is actually very easy. 
When dealing with  stubs for singleton forms, a later stub  will have a copy of 
the source file information  from all  earlier stubs,  plus its own source file 
information; ergo the stub with the  longest list of source file information is 
the last loaded stub for a given singleton form. As such, it's trivial to offer 
the  (file_load_order::get_canonical_instance_of_singleton_form)  function  for 
accessing the form stub for a given singleton form.

All nice and simple.


== Anywho... ==================================================================

There are other major complications that  arise from these forms. One is how to 
handle their  outbound references.  Consider the case of a DOBJ  singleton form 
that refers to some KYWD. Deleting the KYWD form would lead DovahKit to try and 
sever outbound  references from the DOBJ  form stub to the KYWD  being deleted. 
Except here's the thing: what if the singleton form refers to the to-be-deleted 
KYWD form in a dependency, rather than  the active file? Well, that leads to us 
trying to sever outbound references from multiple DOBJ form stubs, not just the 
canonical one, which in turn leads to each of these form stubs being flagged as 
edited.

With the approach in which we copy source  file information between stubs, this 
doesn't have any immediately obvious  consequences. We're still identifying the 
canonical DOBJ stub based on the length of its file list, rather than by trying 
to sort multiple  stubs based on where  in what files they  originated from and 
whether they've been flagged as edited; this  means that flagging multiple DOBJ 
stubs as edited doesn't affect our ability to identify the canonical stub. This 
holds even if the  canonical stub isn't  part of the active  file and has never 
been edited  in it, because  merely flagging a stub  as edited  doesn't add the 
active file to  its file list.  Additionally,  when saving  the active file, we 
only plan on writing the canonical stub  to the file, which means that flagging 
additional  DOBJ stubs as  edited shouldn't affect  our file output  even if we 
don't end up also flagging the canonical stub as edited.

We do need to be  careful when performing post-save form  stub fixup tasks. For 
example, if multiple  stubs for a  singleton form  were flagged as edited, then 
the  non-canonical stubs  will subsequently  fail to save  (because  we're only 
saving the canonical stub); that's normal, and we shouldn't necessarily discard 
those stubs. At  the same time, if we loaded an active file  that had redundant 
records for a singleton form (e.g.  multiple DOBJ records), then we actually do 
want to discard those redundant stubs once they fail to save. Accordingly, when 
discarding form stubs  that failed to save, we need to check  if they represent 
singleton forms  and if so,  we need to  check whether  their source  file list 
includes the active file (which will only be the case if they originally loaded 
from it; we  only add the active file  to the lists of stubs that  successfully 
saved).

As of this writing, it *feels* like having  multiple stubs for a singleton form 
be edited as a result of use info is consequence-free... provided a frontend is 
sure to work only  with the canonical stub, rather than  trying to treat all of 
the stubs for a singleton form type  the same way as form stubs of other types.
