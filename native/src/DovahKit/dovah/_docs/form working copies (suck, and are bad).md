
# Form working copies (suck, and are bad)

DovahKit features loaded form data that is, by default, "managed:" forms refer to each other via `form_reference_t` objects which function as tracked pointers, with setters that keep use info up-to-date bidirectionally. Several parts of the UI, however, need to be able to create and retain their own copies of form-data structs; they need to be able to store form-data locally, edit it without automatically updating Use Info, and then commit it into the backend (with Use Info updated appropriately) all at once if the user clicks "OK."

A sensible design would be to have "managed" and "unmanaged" versions of the form-data types (and any sub-object types therein), with the UI using the latter; metaprogramming could be used to implement conversion between the two.[^sustain] However, I was a lot less skilled at metaprogramming, and a lot less sensible, when I built DovahKit's foundations half a decade ago. So instead, we have the ability to create a single "working copy" of a form's loaded data. In essence, "managed" and "unmanaged" form data use the same underlying class, and the setters on `form_reference_t` just politely decline to update Use Info when fed a "working copy" form.

[^sustain]: In fact, I plan to refactor form data to work exactly this way as part of a post-launch rebuild, and have gotten proofs of concept working in Compiler Explorer.

This is incredibly limiting; among other things, it means you can only overwrite whole forms, bulldozing them in their entirety[^quest-event-conditions], unless you do the work of manually assigning everything field-by-field. It also blurs the line between "managed" and "unmanaged," such that when writing UI code, it's easy to forget that you need to sever uses of to-be-deleted forms yourself. But these two problems -- working with form data wholesale, and making it easy to forget that *you are the manager now* -- actually synergize into an even worse problem, because usually, UIs don't need a *full* copy of the *entire* form.

[^quest-event-conditions]: Quest event conditions are a good example of how working copies are problematic for being insufficiently granular. These conditions are edited  via the Story Manager UI, but are stored on the `QUST` form. Thus, the Quest UI has to leave these conditions untouched, and since the UI implementation for form dialogs is geared toward committing forms wholesale, that means the UI has to go out of its way to avoid clobbering the original data.

For simple form types, like Shout, all of the form's constituent data can be represented in the states of the UI's individual widgets: plop six DKFormPickers in a dialog and Bob's your uncle. For more complex form types, like Quest, not all form data is exposed through unique, individual widgets in the UI all at once; the form-editing dialog for a Quest will only display one quest stage at a time, for example, and so the data for quest stages can't live in the UI widgets; it has to be stored by hand, whether in a custom Qt model or as state on the dialog; this is, indeed, why "working copies" (as a form of state that can be owned by the dialog) were deemed necessary. Ideally, we'd be able to pick and choose where each individual piece of data lives -- in UI-owned unmanaged form data, or in a single widget -- but because the "working copy" system isn't granular enough, we don't get to pick. Instead, state has to be manually copied out of the "working copy" and into those widgets in which it can live, and then synchronized from the widgets back to the "working copy" when it's time to commit changes to the "canonical" form data.

The workaround, to make that ergonomic, was to make it possible to "bind" UI widgets to target values -- for example, bind an individual DKFormPicker to a `form_reference_t&` in loaded form data; bind an individual QCheckBox to a particular bit in a particular `uint32_t&` flags mask; and so on. So for state that can live in a single widget, we bind the "working copy" field to that widget: the value is copied into the widget at bind time, and then we never pay attention to the value that lives in the "working copy;" and then when the widget's value is changed, the widget auto-updates the value that lives in the "working copy." And of course, these widgets are programmed to hook signals on `DovahKitCore`, detect when forms are deleted, and update their own internal state (which also triggers synchronization to the bound field in the "working copy"), thereby avoiding any dangling references.

For more complex state that can't live in a single widget, the typical approach is to manually copy that state out of the "working copy" and into someplace in the UI -- a private property on the dialog, the data of a QAbstractItemModel subclass, et cetera. We then copy that state back into the "working copy" when the dialog is closed. As long as these models also hook signals on `DovahKitCore`, they can sever any uses of to-be-deleted forms within their own internal contents; the data left behind in the "working copy" will dangle, but nothing should ever touch that.

But these factors lead to some pitfalls:

* Since the overwhelming majority of form-data that the UI needs to work with is individual fields, bound to perpetually-available single-purpose UI widgets, 90% of cases where we need to sever uses of a to-be-deleted form are handled automatically by the widgets themselves.

* Therefore, for the other 10% of cases, it's easy to forget to do the severing oneself, within the UI code.

* When you have fields on a form that the UI should never touch[^quest-event-conditions], the UI has to go out of its way, at save time, to transplant those fields from the "canonical" form-data into the "working copy" form-data, so that when the latter overwrites the former, the fields are not clobbered by stale or potentially dangling data.

* Even the 90% of automatic cases are just awkward: we have the "working copy" acting as a transport medium to get the data in and out of the UI, but the "working copy" lives for the entire time the UI is open, with the data inside left untouched, unmanaged, and growing stale until we eventually bulldoze it (with fresh state from the UI) when we go to commit changes to the form. And if there's anything that we *don't* bulldoze and *also* forget to update by hand, then we're committing potentially stale/dangling state into the form. This sucks. It's bad and stupid, *and* dumb.

The last problem -- sort of an overarching issue encapsulating all of the above -- is that "working copies" are conceptually muddled. They're not really type-safe, since, again, they are a means by which a single class can act as both "managed" and "unmanaged" data; they take things that should be done by the frontend, and implement them as part of the backend[^centralized-copies]; and they ultimately produce (or *are*) too fuzzy a boundary between managed and unmanaged data, which in turn makes things like ownership and lifetime semantics (including severing outbound refernces to to-be-deleted forms) fuzzy.

[^centralized-copies]: There is some value in being able to say, "I want *either* this form's committed/canonical data or, if it's currently being edited somewhere, the 'work-in-progress' data." Since working copies are tracked by the form stub from which they were created, you can do this easily. However, that shouldn't be the backend's responsibility; form-stubs shouldn't have pointers to that work-in-progress data; instead, the frontend should maintain a `std::unordered_map<dovah::form_stub*, std::unique_ptr<dovah::base_unmanaged_form_data>>`.
    
    Incidentally, if we get rid of "working copies" and have form-stubs *not* track them, that saves eight bytes that we can put to better use, e.g. by making localized string use info (a thing that doesn't exist yet, but will need to exist in the future; another thing for which I have redesign plans) heap-allocated and spending those eight bytes on a pointer to that, so that form-stubs only burn memory on tracking l-strings when it's necessary.
