
As explained in other documents, DovahKit  doesn't load the full data for forms 
when loading files.  It instead creates an index of the forms that exist across 
the entire load order,  along with their file pointers and offsets, in order to 
be able to load  forms on demand and  unload them when they're  no longer being 
worked with. However, DovahKit loads a little more data than just file offsets.

Every form is given a "form stub," which serves as a representation of the most 
important data for the form: its form ID,  its type, its editor ID, and its use 
info, along with a handful of other  fields. Form stubs are intended to provide 
enough information to perform basic operations  with the form without having to 
load its data in full. The full list of fields is:

   flags
      A set of flags used  to keep track of  run-time-specific characteristics, 
      such as whether the form has been flagged as edited.

   form ID
      The form's form ID, relative to the full load order.

   editor ID
      The form's editor ID, as indicated by the last loaded record.

   use info (inbound and outbound)
      Information used to track references between forms.

   parent form ID
      The form ID of  the form's parent, relative to the full  load order. This 
      information is not part  of the form itself, and  so must be preserved in 
      the stub by the file load process.

   group type
      Used to remember  what GRUP type the form loaded from.  This is currently 
      used to know  whether to save an ObjectReference into a cell's  temporary 
      or persistent child  group (it's saved into the  same GRUP type it loaded 
      from),  but this will likely not be a tenable solution once we  implement 
      world editing.

      It's  currently also  used to tell a worldspace's  persistent cell  apart 
      from its other cells, but that's not how the game does things.

   cell grid coordinates
      Used for exterior cells; loaded from CELL/XCLC.


=== THE CONVENTIONS FOR FILE INFO =============================================

As explained in <how the game loads forms.txt>,  the Rule of One is consciously 
applied by  Bethesda on a  per-form-type basis, rather  than being  an inherent 
limitation of the  engine's form loader. This means that form  stubs need to be 
able to load form data  from all files that supply it.  Accordingly, form stubs 
must remember a file pointer and file offset for every relevant record.

We store this data using a trick  inspired by Bethesda's "BSTSmallArray" class. 
You can think of it like a union between a vector of items and a single item. A 
flag on the form stub indicates whether the stub has a single item or a vector. 
The motivation for  this approach is  memory compactness.  Skyrim.esm alone has 
more than two hundred  thousand forms, which means that  increasing the size of 
the form stub struct  by just four bytes will increase our  memory footprint by 
some 781 KB.  (This is a  simplification; refer to the  section on  stub memory 
management.)


=== THE CONVENTIONS FOR USE INFO ==============================================

Form stubs track use  info bidirectionally:  every stub has  a list of outbound 
connections to forms, and a list of  inbound connections from forms. Both lists 
are maps of form IDs to use info entries.

A use info entry consists of: a pointer to the other form's stub; a flags mask; 
and a refcount.  The refcount is present because one form can  refer to another 
in multiple different ways  at once. Flags indicate  the presence of unique and 
singular relationships, such as parent/child relationships, or the relationship 
between an ObjectReference and its base form. Flags are only suitable for kinds 
of relationships that can only appear once between any two forms.

Parent/child relationships are always implemented as outbound from the child to 
the parent. To put it another way, child  forms are considered "users" of their 
parents. Interestingly enough, the Creation Kit seems to use the same approach, 
likely because it is easy to implement.

After the initial file load, when all  form stubs have been built, outbound use 
info  will be generated by selectively parsing  records, looking only for  uses 
and ignoring everything else. This is a multi-threaded process. Once all of the 
outbound uses have been found, a single-threaded loop is used to "send" them to 
the target forms, which create matching inbound use info.


=== MEMORY MANAGEMENT FOR FORM STUBS ==========================================

As mentioned above, Skyrim.esm alone has over two hundred thousand forms, which 
means that we'll be creating more than  two hundred thousand form stubs when we 
load it. That's a lot of instances to have to allocate individually, so we save 
on memory management by using a  multi-threaded block allocator. Currently, the 
allocator is  configured to  use blocks large enough  to hold sixteen  thousand 
form stubs.

The multi-threaded block allocator's design is as follows: blocks are stored in 
doubly-linked lists.  A block list can be assigned to an  individual thread, or 
it can be retained as a single "unowned" list. When a thread closes, its blocks 
are merged into the "unowned" list; when a new thread spawns, the blocks in the 
"unowned" list are given to it to use.  Threads can allocate memory without the 
need to lock; however, freeing memory requires a lock.
