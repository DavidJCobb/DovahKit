
As explained in other documents, DovahKit  doesn't load the full data for forms 
when loading files.  It instead creates an index of the forms that exist across 
the entire load order,  along with their file pointers and offsets, in order to 
be able to load  forms on demand and  unload them when they're  no longer being 
worked with. However, DovahKit loads a little more data than just file offsets.

Every form is given a "form stub," which serves as a representation of the most 
important data for the form: its form ID,  its type, its editor ID, and its use 
info, along with a handful of other  fields. Form stubs are intended to provide 
enough information to perform basic operations  with the form without having to 
load its data in full. The full list of fields is:

   flags
      A set of flags used  to keep track of  run-time-specific characteristics, 
      such as whether the form has been flagged as edited.

   form ID
      The form's form ID, relative to the full load order.

   editor ID
      The form's editor ID, as indicated by the last loaded record.

   use info (inbound and outbound)
      Information used to track references between forms.

   parent form ID
      The form ID of  the form's parent, relative to the full  load order. This 
      information is not part  of the form itself, and  so must be preserved in 
      the stub by the file load process.

   group type
      Used to remember  what GRUP type the form loaded from.  This is currently 
      used to know  whether to save an ObjectReference into a cell's  temporary 
      or persistent child  group (it's saved into the  same GRUP type it loaded 
      from),  but this will likely not be a tenable solution once we  implement 
      world editing.

      It's  currently also  used to tell a worldspace's  persistent cell  apart 
      from its other cells, but that's not how the game does things.

   cell grid coordinates
      Used for exterior cells; loaded from CELL/XCLC.

   file info
      A list of file  reader pointers and,  for each file,  the offset into the 
      file at which the form's  record header is  located, and the record flags 
      seen in that file.

Form stubs need to  be aware of their owning file load order.  However, they do 
not need to actually retain a pointer to it. File reader instances already have 
a pointer  to their owning  load order, so a form stub  can simply  access that 
through any of its file reader pointers. This does have one caveat: a form stub 
must have a file reader pointer. This means that stubs that aren't actually the 
product of a file load  (e.g. stubs for hardcoded forms)  must be given a dummy 
file to use.

Stubs access their owning load orders to  check whether form loading is blocked 
(e.g. because a save operation is in progress),  to look up other stubs by form 
ID during the use info build process,  to signal when they have been flagged as 
edited so that they  can be tracked as active file forms,  and to check whether 
their parent or child forms are active file forms (during the save process).


=== THE MECHANICS FOR LOADING STUBS ===========================================

Form stubs are built using a multi-threaded  loader: a file is divided into its 
discrete GRUPs, and  these GRUPs are assigned to worker threads.  These workers 
communicate with their  owning file-reader  instances and,  through those, with 
the owning load order instance:  the workers create  form stubs themselves, set 
up the appropriate  file info, and then send the stubs to the  load order to be 
accepted or rejected.

(Actually, there  are two kinds of form  stubs that aren't loaded  using worker 
threads: worldspaces and their persistent cells. These stubs are created during 
the process of assigning GRUPs to worker  threads, so that a worldspace's child 
GRUPs can potentially be loaded by multiple worker threads at a time.)

The load order will handle things like  validating form types on overrides, and 
managing the file lists for singleton forms. When dealing with an override, the 
load order will  copy the file list for  the previously-existing  stub into the 
file list for the new stub,  before then deleting  the previously-existing stub 
and allowing the new stub to replace it. The load order is also responsible for 
taking a file-local form ID and converting it to a load-order-relative form ID.

If the load  order rejects  a form stub (e.g. because  it is a  type-mismatched 
override), then the worker thread should delete the stub.


=== THE CONVENTIONS FOR FILE INFO =============================================

As explained in <how the game loads forms.txt>,  the Rule of One is consciously 
applied by  Bethesda on a  per-form-type basis, rather  than being  an inherent 
limitation of the  engine's form loader. This means that form  stubs need to be 
able to load form data  from all files that supply it.  Accordingly, form stubs 
must remember a file pointer and file offset for every relevant record.

We store this data using a trick  inspired by Bethesda's "BSTSmallArray" class. 
You can think of it like a union between a vector of items and a single item. A 
flag on the form stub indicates whether the stub has a single item or a vector. 
The motivation for  this approach is  memory compactness.  Skyrim.esm alone has 
more than two hundred  thousand forms, which means that  increasing the size of 
the form stub struct  by just four bytes will increase our  memory footprint by 
some 781 KB.  (This is a  simplification; refer to the  section on  stub memory 
management.)


=== THE CONVENTIONS FOR USE INFO ==============================================

Form stubs track use  info bidirectionally:  every stub has  a list of outbound 
connections to forms, and a list of  inbound connections from forms. Both lists 
are maps of form IDs to use info entries.

A use info entry consists of: a pointer to the other form's stub; a flags mask; 
and a refcount.  The refcount is present because one form can  refer to another 
in multiple different ways  at once. Flags indicate  the presence of unique and 
singular relationships, such as parent/child relationships, or the relationship 
between an ObjectReference and its base form. Flags are only suitable for kinds 
of relationships that can only appear once between any two forms.

Parent/child relationships are always implemented as outbound from the child to 
the parent. To put it another way, child  forms are considered "users" of their 
parents. Interestingly enough, the Creation Kit seems to use the same approach, 
likely because it is easy to implement.

After the initial file load, when all  form stubs have been built, outbound use 
info  will be generated by selectively parsing  records, looking only for  uses 
and ignoring everything else. This is a multi-threaded process. Once all of the 
outbound uses have been found, a single-threaded loop is used to "send" them to 
the target forms, which create matching inbound use info.

But what about dangling references between forms? That is, what if one form has 
data that refers to some form ID which  is not actually in use by another form? 
This can occur as a result of incorrect  edits made with community tools (often 
as a result of user error).

One of  the hazards of  on-demand loading is that it  allows for  such dangling 
references to  be invisibly filled in,  when new forms are  created or existing 
forms are renumbered.  Consider the case of a Shout  whose third word refers to 
some unused  form ID 0x0000C0BB. If a user were to create a new  form with that 
form ID,  while the Shout  is unloaded, then upon loading  the Shout,  it would 
effectively  be retroamended  to refer to  the new  form -- without  the user's 
knowledge. If the new form is of an  inappropriate type, then this will produce 
a warning, but not  the right warning; however, if it's of  an appropriate type 
for the dangling reference in question,  then no warning will occur: there will 
be no indication that a change has occurred, even though this change could lead 
to undesired behavior in-game.

The solution to this is "none-stubs."  During the process in which we build all 
inbound use info using the already-built outbound use info, we want to scan for 
dangling references. (Any outbound reference that lacks a form stub pointer has 
to be a dangling reference. We grab the  form stub pointers at the time that we 
create the outbound references, so it should never be possible for a valid form-
to-form reference to lack a pointer to  the referenced stub.) Upon encountering 
any such reference,  we create a form  stub for the  referenced form ID, with a 
form type of "none." In essence, we're using form stubs not simply to represent 
loaded forms, but also form IDs themselves.

"None-stubs" require a number of additional considerations:

 - None-stubs need a dummy file object,  because form stubs access their owning 
   load order via their first file.

 - Not all form stubs with  form type "none" are "none-stubs,"  because nothing 
   is ever simple...  Bethesda defines two hardcoded  "persistence forms" whose 
   form type is "none."  Fortunately, we can check whether  a form stub's first 
   file is the dummy none-stub file, and use that to tell these stubs apart. We 
   provide (form_stub::is_none_stub) which performs this check.

 - None-stubs shouldn't  be placed in a load order's map  of active file forms, 
   even if their form IDs would place them within the active file.

 - When the user attempts to renumber a form to an ID that is in use by a none-
   stub, we need  to sever all references to the none-stub and  then delete it. 
   If this is  not possible  (which should only be the  case while  DovahKit is 
   still  in development, if one  of the referring  forms is of a type  that we 
   haven't implemented editing for), then  the renumbering operation must fail.

 - Form creation  will behave  similarly. The backend  already picks  a form ID 
   automatically; if the selected form  ID is occupied by a none-stub, then the 
   stub needs to be discarded in the same  manner as for form renumbering, with 
   the same possible failures.

   This gets messy when dealing with  form duplication, as duplicating a parent 
   form should also duplicate the children. A non-severable none-stub can cause 
   any of the forms to fail to duplicate, but only a failure of the parent form 
   will halt  the overall  duplication process. No  attempt is made  to prevent 
   this, because this sort of problem should only occur while DovahKit is still 
   in development; once support for all form types is implemented, there should 
   be no case where a none-stub cannot have all inbound references severed.

 - Any none-stubs that  are destroyed by an internal operation  need to trigger 
   the "form loss" callback.

 - When serializing  a form-to-form reference, we should  write zero instead of 
   the referenced  form stub's form ID  if the referenced stub  is a none-stub. 
   This is handled by returning  false when  (file_writer::_can_serialize_form) 
   is called for a none-stub.

 - After a save operation,  none-stubs must be deleted  from memory if they are 
   unreferenced or if they are referred  to only by active file forms (i.e. the 
   forms that have just been saved). We need to refrain from deleting any none-
   stubs that are referred  to by non-active file forms,  as doing so will flag 
   those forms as "edited."


=== MEMORY MANAGEMENT FOR FORM STUBS ==========================================

As mentioned above, Skyrim.esm alone has over two hundred thousand forms, which 
means that we'll be creating more than  two hundred thousand form stubs when we 
load it. That's a lot of instances to have to allocate individually, so we save 
on memory management by using a  multi-threaded block allocator. Currently, the 
allocator is  configured to  use blocks large enough  to hold sixteen  thousand 
form stubs.

The multi-threaded block allocator's design is as follows: blocks are stored in 
doubly-linked lists.  A block list can be assigned to an  individual thread, or 
it can be retained as a single "unowned" list. When a thread closes, its blocks 
are merged into the "unowned" list; when a new thread spawns, the blocks in the 
"unowned" list are given to it to use.  Threads can allocate memory without the 
need to lock; however, freeing memory requires a lock,  and locking also occurs 
when threads open and close,  regardless of whether they ever actually allocate 
any form stubs.

This doesn't result in us totally avoiding  all locking, as locks are still hit 
when we actually insert  new form stubs  into the  file load order's form maps, 
but  heap-related locks should only be hit after every sixteen thousandth  form 
stub.
