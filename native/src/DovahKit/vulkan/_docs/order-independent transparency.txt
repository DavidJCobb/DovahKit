
Rendering objects with alpha transparency can be rather tricky. The traditional 
way to do alpha blending is affected by the order in which objects are handled; 
it matters which object is "over" and which object is "under." However, getting 
this information requires some sort of depth sorting, which can be expensive... 
and can be vulnerable  to nasty edge-cases,  as can be seen  with the painter's 
algorithm.

Such is the motivation for "order-independent transparency,"  a family of alpha 
blending techniques which seeks to avoid  the need to depth-sort the objects to 
be drawn prior to rendering.  Note that OIT techniques don't necessarily try to 
avoid sorting altogether.

One simple approach [1] to OIT is to  render transparent objects in two sets of 
draw calls.  The first pass, for color, draws to an "A-buffer" image,  which is 
used to hold data about each pixel in the final render: the RGBA colors and the 
depth values for up to N fragments per pixel. The second pass, for compositing, 
scans the A-buffer, sorts the stored fragments, and blends them. If more than N 
fragments end up on the same pixel (i.e.  more than N transparent objects cover 
the same pixel on-screen), then the extra fragments are "tail-blended."

This approach allows per-pixel  sorting within the shader; however, it can only 
process and store fragments in the order they're  encountered, which means that 
nearer fragments may be tail-blended  while further fragments are rendered more 
faithfully.

An alternative to  this approach is blended order-independent  transparency, or 
BOIT. This technique takes the approach of making the blending operation itself 
order-independent:  instead of using a traditional alpha blend,  a custom blend 
function is used and applied to unsorted fragments.  McGuire and Bavoil offer a 
good overview of the technique [2], describing it mathematically first and then 
offering snippets  of OpenGL code. I'd like to reproduce some  of the equations 
here, but this is a plain-text document, so let me define some notation:

   SUM(index, from, to, expression)

      Notation for the capital-sigma notation for mathematical summation.

   MUL(index, from, to, expression)

      Notation for the capital-pi notation  for the product of a sequence (i.e. 
      the same as SUM, but with multiplication).

The equations we'll be displaying here use the following variables:

   C = RGB color with premultiplied alpha
   a = alpha component

   n = number of fragments to blend

   C0 = background RGB color that we're rendering onto
   Cf = final RGB color to render
   Ci = i-th RGB being rendered
   ai = i-th alpha value being rendered
   
When rendering, we end up receiving one fragment at a time, with no way to know 
in advance how many fragments we'll receive (indeed, our inability to have that 
information is the  problem we're trying to solve).  However, the equations are 
written in terms of a known number of fragments N.

Meshkin developed the first approach to BOIT, and used this equation:

   Cf = SUM(i, 1, n, Ci) + C0 * (1 - SUM(ai))

In simpler terms:  each fragment's RGB color components  are added together. We 
then take the sum of all fragments' alpha values, subtract it from 1 (which may 
produce a negative value),  multiply that by the background color, and add that 
to the sum of the fragments'  RGB values. When multiple  fragments are blended, 
the RGB sums  will likely exceed 1, but the inverted alpha sum will likely fall 
into the negatives, canceling that excess out to some extent.

This equation is, of course,  quite imperfect,  and can produce very inaccurate 
colors (though the final alpha transparency  is always correct). This brings us 
to weighted blended  order-independent transparency (WBOIT),  an improvement on 
BOIT proposed by McGuire and Bavoil.

McGuire and Bavoil  start by presenting an improvement  on older BOIT equations 
designed by Bavoil and Myers:

   Cf = (SUM(i, 1, n, Ci) / SUM(i, 1, n, ai)) * (1 - MUL(i, 1, n, (1 - ai)))
      + C0 * MUL(i, 1, n, (1 - ai))

We start by  summing all of the RGB (with premultiplied alpha)  values for each 
of the fragments, and then dividing that  by the sum of the alpha values. Next, 
we divide that by  the inverted product of all inverted alpha  values: that is, 
we invert all of the alpha values,  multiply them together, and then invert the 
result. This is the "over" color -- all of our transparent objects' combined to 
one set of RGB values, to be drawn overtop the background.

The "under"  color's RGB, meanwhile,  is scaled by the product of  all inverted 
alpha values. In pseudocode, we may express this as:

   fragment background; // color
   fragment inputs[];   // color, vertex position, anything else relevant
   fragment final;      // color

   float alpha_sum = 0.0;
   for(auto& c : inputs) {
      alpha_sum += c.a;
      final.rgb += c.rgb;
   }
   final.rgb /= alpha_sum;

   float inv_alpha_prod = 1.0;
   for(auto& c : inputs) {
      inv_alpha_prod *= (1 - c.a);
   }

   final.rgb      *= 1 - inv_alpha_prod;
   background.rgb *= inv_alpha_prod;
   
This pseudocode isn't even remotely close  to the code we'd use to handle WBOIT 
because again, we don't have foreknowledge of all fragment colors to blend; our 
lack of that foreknowledge is what  (W)BOIT is meant to compensate for. Rather, 
that pseudocode is just an alternative to  mathematical notation for those like 
me who struggle with it.

Note that the above  is still BOIT, not  WBOIT. We aren't  weighting any of the 
values. Let's add a placeholder function for weighting, for WBOIT:

   fragment background; // color
   fragment inputs[];   // color, vertex position, anything else relevant
   fragment final;      // color

   float function weight(depth, alpha) {
      // ...
   }

   float alpha_sum = 0.0;
   for(auto& c : inputs) {
      float w = weight(c.depth, c.a);
      //
      alpha_sum += w * c.a;
      final.rgb += w * c.rgb;
   }
   final.rgb /= alpha_sum;

   float inv_alpha_prod = 1.0;
   for(auto& c : inputs) {
      inv_alpha_prod *= (1 - c.a);
   }

   final.rgb      *= 1 - inv_alpha_prod;
   background.rgb *= inv_alpha_prod;

We'll actually define the weighting function later. All we need to know for now 
is that for each  fragment, it takes  the fragment's  camera-relative depth and 
the alpha value, and it returns a float  that gets used to scale the fragment's 
influence on the  "over" color's RGB components. That "weight"  float should be 
positive, and the depth value should decrease away from the camera.

Remember that blending the fragments'  alpha values in an order-independent way 
is  easy; the challenge is to compute RGB  components that resemble a  properly 
ordered blend of each fragment.  The weighting we use  here allows a fragment's 
depth and alpha to influence its impact on the blended RGB, as a rough but good 
substitute for ordering.


=== IMPLEMENTING THIS IN A RENDERER ===========================================

How, then, do we convert the above into  something we could put into a fragment 
shader? Well,  note first that the above pseudocode is functionally  equivalent 
to the following rearranged pseudocode:

   fragment background; // color
   fragment inputs[];   // color, vertex position, anything else relevant
   fragment final;      // color

   float function weight(depth, alpha) {
      // ...
   }

   float alpha_sum      = 0.0;
   float inv_alpha_prod = 1.0;
   for(auto& c : inputs) {
      float w = weight(c.depth, c.a);
      //
      alpha_sum += w * c.a;
      final.rgb += w * c.rgb;
      //
      inv_alpha_prod *= (1 - c.a);
   }

   final.rgb /= alpha_sum;
   final.rgb      *= 1 - inv_alpha_prod;
   background.rgb *= inv_alpha_prod;

So for every pixel, we first need to loop over all of the relevant fragments to 
compute a few values; then, outside of that loop, we need to apply those values 
and get the final color for the pixel.

Within the loop,  we don't need to know any of the fragments'  indices, nor the 
total number of fragments  (as shown by my use of  ranged-based for-loop syntax 
above). Conceptually, this is the same as just running the loop body within the 
fragment  shader when  drawing the scene; "loop over  all of the  fragments" is 
really just "run this code for each fragment," which is how our fragment shader 
would be invoked by default when drawing the whole scene.

Code outside of  the loop is per-pixel rather than per-fragment.  We can handle 
this by doing a second draw operation:  if we draw a full-screen polygon with a 
separate shader, then each pixel is  its own fragment, and that shader could be 
engineered to access  the values computed when we drew  the whole scene as part 
of our loops.

Accordingly, we can divide our render process as follows:


 - We use two passes: first, a color pass to serve as the loop body, wherein we 
   draw the whole scene; then, a composite pass to serve as the code outside of 
   the loop, wherein by drawing a full-screen polygon we can take the per-pixel 
   data computed in the color pass and apply it on a per-pixel basis.


 - We need some way  to actually get data from the color pass  to the composite 
   pass. In practice,  we can render to  two textures: an  RGBA texture for the 
   "final" color,  and an A-only texture for the "inv_alpha_prod"  variable. We 
   will call these the "accumulator" texture and the "reveal" texture.

   Why two textures? Well, really, we just need to store five values per pixel, 
   and a color channel is just a  value per pixel...  but there's no such thing 
   as an image with five color channels, so we instead use two images: one with 
   four color channels and another with just the one channel.

   The values  that we want  to compute in our loop need  to be initialized  to 
   different numbers  (0 for the sum; 1 for the multiplication).  We can handle 
   this by using VkClearValues.


 - There's one more bit of trickery that we can rely on. Hypothetically, during 
   the color pass,  we could manually read the preexisting  values for a pixel, 
   compute  the values for the current  fragment, and manually add or  multiply 
   them in as needed.  However, what if we could get the  GPU to do that for us 
   with no effort  needed on our part?  What if there were some  operation that 
   the GPU was really good  at, and that it's going to  have to do anyway, that 
   we could co-opt for our needs?

   As it happens, there is:  the blend settings for  the shader pipeline. These 
   control how a  new fragment is drawn overtop the previous  fragments and the 
   background.

   Every blend  operation involves  multiplying  the "over" and  "under" colors 
   (more formally called the "source"  and "destination") by some chosen value, 
   and then adding the results together.  This means that if we get clever with 
   those values,  we can have the GPU handle the additions  and multiplications 
   in our color pass (our loop body) for us, with literally no added work.

   Here, we see another  benefit of using  two separate  images: we can specify 
   different blend settings for each image.



==== THE COLOR PASS ===========================================================

So let's start  with our color pass, then. Our fragment shader  will be drawing 
to two textures, so it'll produce two  outputs: a color for the accumulator and 
a color for the reveal texture.

For the accumulator, the shader will return the fragment's weighted RGBA. We'll 
use VK_BLEND_FACTOR_ONE  for both the source and destination,  which means that 
the value we return will be added to  the value that's already present. That'll 
get us summation for free.

For the reveal image,  the shader will return the fragment's  weighted A. Here, 
we'll use  VK_BLEND_FACTOR_ZERO for  the source, which prevents the  returned A 
from  being added. We'll also use  VK_BLEND_FACTOR_ONE_MINUS_SRC_ALPHA for  the 
destination; because our source is  alpha-only, this means that the destination 
gets multiplied by one minus the value we've returned:

   result = (src * 0) + (dst * (1 - src))
   result = dst * (1 - src)

If the reveal image is initialized to all-white (1.0), then that reproduces the 
multiplication loop and computes the "inv_alpha_prod" variable.

These techniques could theoretically be  used for any operation wherein we need 
to sum or multiply values per-fragment.


==== THE COMPOSITING PASS =====================================================

With the color pass done, we move onto the compositing pass. We want to use the 
per-pixel values computed within the  color pass to actually draw to our scene. 
All we need to do is have a second fragment  shader draw a full-screen polygon; 
it can sample from the accumulator and reveal textures, with each fragment that 
it handles effectively corresponding to one on-screen screen pixel.

Within the  compositing pass, there's  only one blend left to  perform: that of 
the combined transparent  objects onto the preexisting  background. We start by 
taking  the accumulator color and dividing its RGB by its A; that gives  us the 
division after the first loop in our pseudocode, and gets us the source color's 
final RGB. We'll also take the reveal  color (which is just an alpha component) 
and use that directly for the source color's final A. We then return the source 
color.

We'll use VK_BLEND_FACTOR_ONE_MINUS_SRC_ALPHA  for the source color, along with 
VK_BLEND_FACTOR_SRC_ALPHA for the  destination. The former blend factor handles 
multiplying  the source color by  (1 - inv_alpha_prod),  and the latter handles 
multiplying the destination (background) color by (inv_alpha_prod).

And with that, we're done! We've implemented  a commutative (order-independent) 
blend function, and we've made creative use of intermediate textures and native 
blend functions to carry out that blend as optimally as possible.

With the overall process out of the way,  we now need to focus on the specifics 
of our weighting function.


==== THE WEIGHT FUNCTION ======================================================

There are a few considerations that go into this.

First: the weight  function is  applied to  the RGB sum and  the A sum, and the 
former sum is then divided by the latter sum. This means that weights are on an 
arbitrary scale: mathematically, it doesn't matter how large or small they are, 
because that  division serves to normalize them. This means that  we can choose 
the scale that weights exist on based  on whatever technical limitations become 
relevant.

Let's start with one technical limitation:  the numeric precision we're limited 
to when doing  the OIT calculations. If we wanted to, we  could use traditional 
32-bit floating-point numbers for our  color channels; however, that would mean 
twenty bytes of OIT  data for every pixel in the render  area. If we use 16-bit 
floats instead, then we need only ten  bytes of OIT data per pixel; however, we 
then have less precision and a smaller range of values to work with.

Signed 16-bit floats cover the  range (+/-)65504.  The minimum value above 1 is 
1.0009765625, or (1 + 1/1024). Between  128 and 256, the epsilon is 0.125, with 
the epsilon  doubling in  synch with the range  (i.e. between 256 and  512, the 
epsilon is 0.25). McGuire and Bavoil propose a few equations that are optimized 
for this range of precision given depth values in the range of [0.1, 500]:

   alpha * std::clamp(
      10 / (
         0.00001
         + std::pow(fabs(depth) /   5, 2)
         + std::pow(fabs(depth) / 200, 6)
      ),
      0.01,
      3000
   );

An alternate equation "pushes the knee of the curve," improving quality for any 
objects near the middle of the depth range  but sacrificing quality for objects 
at the edges of the range:

   alpha * std::clamp(
      0.3 / (
         0.00001
         + std::pow(fabs(depth) / 200, 4)
      ),
      0.01,
      3000
   );

The alpha component (in the range [0, 1]) is multiplied in to ensure that a low-
opacity surface close to the camera  doesn't exert undue influence on the pixel 
color, overwhelming  the color of more  opaque surfaces in the  distance. Given 
an alpha of 1.0,  we reach the maximum weight  3000 at any depth up  to roughly 
(+/-)0.288241, for the first equation; we reach the minimum weight at any depth 
at or past roughly (+/-)158.095. With the second equation, we reach the maximum 
weight at any depth up to around (+/-)19.4801; we hit the minimum weight at any 
depth at or past roughly (+/-)468.069.

Now, you may have a few questions about that:

 - If typical  depths within your renderer  fall within a different  range, how 
   might you adjust this equation to better compensate?

 - For that matter, how did McGuire and Bavoil design the equation in the first 
   place? How would we design our own?

The only advice they offer for deriving equations like these is:

 - "Rational polynomial weights"  that  "exhibit slower asymptotic growth"  are 
   needed because exponential functions would blow past the precision limits of 
   16-bit floats.

 - The explanation for using the alpha component that I mentioned above.

 - Clamping in general  is needed to prevent overflow and  underflow, which can 
   occur when the alpha is large and the depth, small.

 - If you draw a log-log graph of McGuire  and Bavoil's equations -- that is, a 
   graph with logarithmic rather than  linear axes, such that x^2 and x^3 would 
   render as  straight lines -- then you'll see that they start  off horizontal 
   and then bent downward with a brief curve, before flattening into a downward 
   and rightward line. McGuire and Bavoil advise "pushing the knee of the curve 
   towards the upper right" as a way of improving rendering on objects near the 
   middle of the depth range, at the  cost of weakening rendering on objects at 
   the edges of the range. Given an  equation and its log-log-graph equivalent, 
   do you know how to not only make adjustments to the latter but also backport 
   those to the former? Because I don't.

Your next question is probably: why is this dilemma relevant?

Recall that the  equations are designed  for a depth range  of [0.1, 500] in an 
environment that uses 16-bit floating-point values. 500 units may be a moderate 
or large distance in some renderers,  but it's very short within Skyrim's world 
scaling; one unit  is closer to an inch than a foot. A cell is 4096  units long 
on a side, so if our camera  is positioned at the  center of a cell and we want 
to cover  a range of up to three  cells out, that would be a distance of 10240, 
or  4096 * 2.5,  which is significantly larger than 500.  How would we create a 
weighting  function that adequately handles values along this range?  How would 
we account for 16-bit floating-point  imprecision? No idea. My best guess is to 
divide the depth values by 20 going in, scaling 10240 down to  512. Would there 
be issues with granularity? Over how far a range can we stretch these equations 
before they become unworkable? No idea.

Do we even need to stretch the range? The equations are balanced for [0.1, 500] 
yet one caps out at 158. I s'pose I won't know until I not only implement WBOIT 
but also test the renderer in a worldspace.
