
Imagine that our Render Window editor has a "camera speed" setting that exactly 
mimics the "camera speed" setting from Halo 5's "Forge" map editor. The setting 
would have three values representing camera movement speed multipliers: Normal, 
Precision, and Boost. For now, assume the user has an Xbox controller.

If the user clicks the left stick briefly, then they'll toggle the camera speed 
between Normal and Precision, the latter slowing the camera down for more fine-
tuned movement. If the user clicks and  holds the left stick, then we switch to 
Boost, a much faster speed; when the  stick is released, we switch to whichever 
speed value the user activated previously.

In order for our controls to behave similarly, we need to define an editor tool 
called  "Set Camera Speed." This tool needs to communicate with the  editor and 
instigate changes in the "camera speed" enum.  The editor in turn must maintain 
two values for the enum: a "persistent"  value and a "temporary" override, with 
the "current" value defined as the temporary value if present or the persistent 
value otherwise. We can express the editor state as follows:

   template<typename Enum> struct EditorEnum {
      Enum persistent;
      std::optional<Enum> temporary;

      inline Enum current() const {
         if (temporary)
            return temporary.value();
         return persistent;
      }
   };

   enum class CameraSpeed {
      Normal,
      Precision,
      Boost,
   };

And we can define the tool as follows:

   class set_camera_speed : public base {
      public:
         //
         // ... boilerplate ...
         //

         struct options {
            CameraSpeed value = CameraSpeed::Normal;
         };
         struct results {
            //
            // This "results" struct will be passed to the editor after inputs 
            // are processed.
            //
            std::optional<CameraSpeed> temporary;
            std::optional<CameraSpeed> persistent;
         };
         
         virtual void set_camera_speed::invoke(
            const input_result&        ir,
            const opaque_option_union& options,
            combined_tool_results&     all_results
         ) const override {
            const auto* o = option_union::as<options>(raw_options);
            if (!o)
               return;
            results res;
            auto&   editor = SomeSingleton::get();
            if (ir.type == control_type::button) {
               if (ir.button.press_type == button_press:type::while) {
                  res.temporary  = o->value;
               } else {
                  res.persistent = o->value;
               }
            }
            all_results.merge_member(res);
         }
   };

There is one slight  problem with that approach, however:  what happens if this 
same tool  is mapped to multiple "while-down" buttons, with different  options? 
This problem will perhaps be easier to  examine if we generalize it to a larger 
enum, so let's:

   enum class PaintbrushColor {
      White,
      Black,
      Red,
      Blue,
      Green,
      Gold,
   };
   
Let's say we have a tool  that can modify the current  paintbrush color. If the 
tool is  set to  trigger on a single button press (whether a  brief  "tap" or a 
longer "hold"), then it sets the editor's current paintbrush color. If the tool 
is set to trigger while a button is held, then it temporarily changes the color 
until that button is released.

Consider now the following binds:

   Tap   Q | White
   Tap   W | Black
   Tap   E | Red
   While A | Blue
   While S | Green
   While D | Gold

Consider also this sequence  of inputs. How should the  paintbrush color change 
with each input?

   Q Down
   Q Up (tap)
   A Down
   A Up
   W Down
   W Up (hold)
   A Down
   D Down
   S Down
   D Up
   S Up
   A Up

The desired behavior would be as follows:

   Q Down      | Do nothing (non-"while" buttons react when released).
   Q Up (tap)  | Switch the paintbrush color to White.
   A Down      | Switch the paintbrush color to Blue.
   A Up        | Switch the paintbrush color to White.
   W Down      | Do nothing (non-"while" buttons react when released).
   W Up (hold) | Do nothing (the button was held too long to be a "tap").
   A Down      | Switch the paintbrush color to Blue.
   D Down      | Switch the paintbrush color to Gold.
   S Down      | Switch the paintbrush color to Green.
   D Up        | Do nothing ("While S" continues to execute; stay Green).
   S Up        | Switch the paintbrush color to Blue.
   A Up        | Switch the paintbrush color to White.

You can see that when multiple "while" buttons are bound to this same tool, and 
when multiple of these buttons are down  at the same time, the desired behavior 
is for the most recently pressed of these buttons to take precedence. This tool 
needs to be "strictly ordered." How do  we ensure that the inputs are processed 
chronologically, however?


== Here's how strict ordering works ===========================================

DovahKit stores control schemes as  tree structures, and processes inputs in an 
"upward" order to ensure that inputs deeper  into the tree will shadow an input 
shallower in the tree. That is: if [X] is defined as a modifier key, and if [G] 
and [X + G] are mapped to different tools (or options), then pressing [G] while 
holding [X] should trigger only the [X + G] bind and not the [G] bind. Within a 
frame, then, we process inputs in  (depth-inverse) (sub)tree order, rather than 
in the order  the buttons originally went down. There are a  few ways to impose 
chronological ordering on this:

 a) When we detect that a tool's input has been satisfied, check the timestamp. 
    Maintain a chronologically ordered  list of tools to trigger, and after all 
    bound inputs have been checked, trigger the tools within the list.

 b) Allow tools to "merge" their results, and enforce chronological ordering at 
    merge time.

Approach "A" would  require creating, managing, and  destroying a list on every 
frame; we would also need to implement  our own list type in order to avoid the 
overhead of heap allocations and frees per  frame. Approach "B" takes advantage 
of infrastructure that we already need  in order to allow tools to pass results 
to an editor.

Here's the appraoch we went with:

 - The (combined_tool_results) struct is used during input processing to hold a 
   "results" struct for every tool that has one. This struct also has a list of 
   (timestamp_t) values for each tool that requires strict ordering.

 - When a tool is invoked, it's given a  reference to a (combined_tool_results) 
   instance. The tool needs to create  an instance of its "results" struct, set 
   that instance's  values as appropriate, and then call  a function to "merge" 
   the temporary "results" instance into  the "combined tool results" instance.

 - The function in question is:

      template<typename R>
      void combined_tool_results::merge_member(const input_results&, R& r);

   This function checks the input to see  if its timestamp is relevant (i.e. is 
   the input a "while"  button), and then merges the  results objects such that 
   the most  recent one overrides the  least recent one. Each tool's  "results" 
   struct can optionally  define a "merge"  function whose  argument is a newer 
   "results" instance; the "merge_member" function thus does something like:

      // given "a" is the existing results and "b", the results that the tool 
      // just produced:

      if (timestamp_a <= timestamp_b) {
         a.merge(b);
      } else {
         auto temp = b;
         temp.merge(a);
         std::swap(a, temp);
      }
      
As of this writing,  tools are opted into  strict ordering  if these conditions 
are met:

   a) The tool defines a "results" struct.

   b) The "results" struct defines an appropriate "merge" member function.

   c) The tool's compile-time options set (use_strict_ordering) to (true).
