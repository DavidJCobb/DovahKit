
Currently, "DK3D" refers to our systems  for managing and handling input to any 
3D views in DovahKit. We should accept not  only keyboard and mouse inputs, but 
also Xbox controller  inputs. The user should be able  to define custom control 
schemes, and we should also be able to  predefine a variety of wildly different 
control schemes as built-ins. The current  design goal is to offer three built-
in control schemes:


   CREATION KIT STANDARD

      A keyboard-and-mouse control scheme that mimics the Creation Kit's inputs 
      as closely as possible.


   REACHING OUT

      An Xbox controller scheme that mimics the controls used for Halo: Reach's 
      "Forge" map editor,  with adjustments made as  appropriate for DovahKit's 
      different editing functionality.


   EN GUARD

      An Xbox controller scheme that mimics the controls for Halo 5: Guardians' 
      "Forge" map editor,  with adjustments made as  appropriate for DovahKit's 
      different editing functionality.


Here, we see  some dramatically different  functionality. Let's  look at camera 
movement as a simple example:


   CREATION KIT

      Click and drag in the  Render Window with the middle  mouse button to pan 
      the camera.
      
      
   REACHING OUT

      When no objects are selected, all movement is camera-relative and without 
      constraints. The Left Stick allows you  to move camera-lateral, i.e. move 
      forward, backward,  left, or right. The Left Bumper  allows you to strafe 
      camera-down; the Right Bumper, camera-up.

      When an object is selected, this behavior changes. The Left Stick remains 
      camera-relative but all movement is constrained to the world XZ (lateral) 
      plane. The Left Bumper and Right Bumper become world-relative.


   EN GUARD

      Same as "Reaching Out," except that  vertical movement is mapped to A and 
      B instead of Left Bumper and Right Bumper.


We see some very different behavior between  the three control schemes. A naive 
approach to resolving this would be to implement several different functions to 
move the camera, so that inputs can be mapped to them as appropriate:

 - Move Camera (Pan)
 - Move Camera (Strafe Lateral)
 - Move Camera (Strafe Up)
 - Move Camera (Strafe Down)

However, this is an approach that doesn't  scale well at all, particularly when 
generalized to other editor functions.  For example, when painting heightmapped 
terrain in the Creation Kit, you can modify the brush size by 1 using either of 
the square bracket keys, but you can also  set the brush size to any value from 
1 to 9 by pressing those specific keys. Should we implement nine different "Set 
Brush Size" functions and two "Modify Brush Size" functions, for each key?

Here's a better approach: implement a  small number of tools, but allow each to 
define an "options"  struct as appropriate.  Allow each bound  input to specify 
options for its bound tool. We can have just one "Modify Brush Size" tool, with 
an option to modify  or set the brush  size, and a value;  we can have just one 
"Move Camera" tool, with a variety of options to configure its behavior.


== IMPLEMENTATION =============================================================

Every tool is a singleton defined in the DK3D::tools namespace, subclassing the 
DK3D::tools::base class. Tools can optionally define a nested "results" type, a 
nested "options" type, and they can optionally override this superclass member:

   static constexpr compile_time_tool_options compile_time_options = {};

Each tool must override the virtual  "invoke" function, which takes input data, 
a struct containing tool options, and a struct containing all tool results. The 
received options are an opaque tagged  union type; tools can retrieve their own 
options as follows:

   const auto* o = option_union::as<options>(raw_options);
   if (!o)
      return;

A tool that has  results must create an  instance of its results  struct on the 
stack and configure it appropriately  in response to the input being processed. 
The tool must then merge those results into the "all results" argument:

   results res = {
      // ...
   };
   //
   // ...
   //
   all_results.merge_member(input, res);

There are a few reasons we do things this way.

The union of tool options is opaque in  part to limit how much code needs to be 
recompiled when adding, removing, or changing tool classes. The union is broken 
into an opaque superclass, containing only the tag, and a subclass which brings 
in all tool options types. The subclass  is generated at compile-time, to avoid 
the need to manually update the union (or  a variety of other code) when adding 
or removing tools. The union relies on a byte array and pointer casts. (This is 
preferred over std::variant to avoid everything that ever passes a union around 
having to include each of its constituent  types i.e. every tool. We could have 
simply used an std::variant as a field on the "subclass" half of our union, but 
that would've cost us the ability to check the union's tag (e.g. to identify an 
empty union) without having to include all constituent types.)

The collection  of all tool results is a subclass of a std::tuple  generated at 
compile-time to hold the results structs of all tools that define any. We offer 
several helper functions on this subclass to make it easier to access and merge 
in results as appropriate.


== TOOL INVOCATIONS ===========================================================

Tools are invoked under any of the following conditions:

 - The control that they're mapped to has become active in some way

    - A "Tap" or "Hold" button has been released

    - A "Scalar" or "Vector" control has a non-zero value
    
 - The control  that they're  mapped to is a  "While" button,  and is currently 
   down or has just been released

It is the tool's responsibility to handle each case appropriately; for example, 
the "Move Camera"  tool has no  needed behavior  for when a  "While" button has 
been released, and so should simply return immediately in that case (no need to 
even create a no-op "results" struct).

Tool results should be scaled appropriately as well:

 - Scalar, vector, and "while"-button  inputs should be treated as something to 
   do over time; values returned should be in some appropriate unit per second.

 - Non-"while" button inputs should be treated as something to do instantly one 
   time; values returned should be in an appropriate unit.

As an example, the "Move Camera" tool can return (15, 0, 0) when invoked. If it 
was invoked  as an input "over time," then this input dictates  that the camera 
should move at a rate of 15 units per  second; when input handling is finished, 
this value will be scaled according  to the current frame time. However, if the 
tool is instead invoked as an "instantaneous" input, then the value will not be 
scaled at all, and the camera will simply jump by 15 units.
