
When designing a  customizable input system,  one important question to ask is: 
what kinds of inputs are actually representable in this system?


== THE VARIOUS KINDS OF BUTTON MAPPINGS =======================================

The most basic input systems allow  users to map one button to one action. Some 
more advanced systems might allow users to map button combinations,  or allow a 
user to distinguish between different  kinds of button presses (i.e. long press 
versus normal press). For DovahKit, however, we need a much more advanced model 
in order to account both for irregularities within the Creation Kit's mappings, 
and the variety of gamepad control schemes we wish to offer at launch.

Let's first consider button press types. We offer three:

   Press:
      Activate a bound function each time a button is pressed briefly, and then 
      released.

   Long Press:
      Activate a bound function each time a button is pressed, held for a short 
      duration, and then released.

   Hold:
      Activate a bound function continuously whenever a button is down.

There are also  two other kinds of groupings we need to consider:  concurrency, 
and ordering. Here, it's useful to use Windows standard "accelerator keys" as a 
case study. Let's look at the keybind to open the Task Manager: it's most often 
represented as:

   Ctrl + Shift + Esc

This is an accelerator key:  it consists of zero or more  modifier keys, paired 
with exactly  one non-modifier key. The Windows API makes it easy  to implement 
this sort of key combination. Notably,  the modifier keys may be pressed in any 
order; however, they must be pressed  before the non-modifier key, and all keys 
in the bind  must be down at the same time for the bind to trigger.  Let's look 
at some input sequences and see if they trigger the bind.

   INPUT SEQUENCE #1
      [keydown] Ctrl
      [keyup]   Ctrl
      [keydown] Shift
      [keyup]   Shift
      [keydown] Esc
      [keyup]   Esc

      Result: Nothing happens.

   INPUT SEQUENCE #2
      [keydown] Ctrl
      [keydown] Shift
      [keydown] Esc

      Result: Task Manager opens as soon as Esc goes down.

   INPUT SEQUENCE #3
      [keydown] Shift
      [keydown] Ctrl
      [keydown] Esc

      Result: Task Manager opens as soon as Esc goes down.

   INPUT SEQUENCE #4
      [keydown] Shift
      [keydown] Esc
      [keydown] Ctrl

      Result: Nothing happens.
      
We can see from these tests that the modifier keys are unordered: you may press 
them down in any order to trigger the bind; but the bind itself is ordered: you 
must press Esc  after the modifier keys.  Additionally, the bind  requires that 
all of its constituent inputs be down at the same time: it is concurrent.

Let's look at a few more keybinds. We'll annotate concurrency and ordering with 
the following syntax:

   (Unordered Keys)
   [Concurrent Keys]

Here's our list.

   [(Ctrl + Shift) + Esc]
      Opens the Task Manager in Windows.

   [Ctrl + S]
      The "save current file" hotkey in most Windows applications.

   [S + LMB Drag on Selected Ref]
      The "scale selected refs" keybind in the Creation Kit.

   [(Ctrl + Alt + S) + LMB Drag on Selected Ref]
      The "modify light intensity/fade" keybind in the Creation Kit.
      
   Up + Up + Down + Down + Left + Right + Left + Right + B + A + Start
      The  "Konami code"  commonly seen as an easter egg in games and software. 
      Every keypress is ordered but non-concurrent.

      
== REPRESENTING THESE DETAILS IN DOVAHKIT =====================================
   
The easiest way to represent concurrency  and ordering in DovahKit is to assume 
that binds are ordered and non-concurrent by default, and then allow buttons in 
a bind to be grouped into unordered and concurrent inputs.  The first choice we 
must make, then, is how to nest these groupings:  should we have concurrency be 
the outermost grouping and ordering, the innermost, or vice versa?

All of the binds above are representable as concurrency groups that contain the 
ordering groups, so we'll have concurrency be the outermost group.

As such, a bound input is structured accordingly:

 - The button press type is a property of the entire bound input.

 - Mapped buttons are stored as an ordered list of groups of concurrent inputs, 
   and the latter groups are an ordered list of unordered groups.

Suppose we use the following punctuation to represent concurrency and ordering:

   {Non-concurrent keys}
   [Concurrent keys]
   <Ordered keys>
   (Unordered keys)

Our Task Manager bind, then, would look like this,  where the curly bracket and 
angle bracket delimiters are part of the bound input structure:

   {< [(Ctrl + Shift) + (Esc)] >}

The Konami code, meanwhile, would look like this:

   {< [(Up)] + [(Up)] + [(Down)] + [(Down)] + [(Left)] + [(Right)] + [(Left)] + 
      [(Right)] + [(B)] + [(A)] + [(Start)] >}

You can see that single keys are represented as single-item groups. This allows 
us to handle these key combinations in a uniform fashion,  and if we use custom 
list implementations (e.g. a "small vector" struct that can store some quantity 
of list items locally before falling back to heap allocation),  then we can use 
this design without too much memory inefficiency.


== WHAT ABOUT MOUSE MOVEMENT AND JOYSTICKS? ===================================

For most of this document, we look exclusively at button controls.  However, we 
must consider two other kinds of controls as well: "scalar" controls, which can 
produce values along a single axis; and "vector" controls, which produce values 
along two axes. The triggers on an Xbox gamepad are scalar controls; the sticks 
are vector controls. Mouse movement is also a vector control.

Consider the following binds from various applications:


   LMB Down on selection + Mouse Move

      Drag-move the selected ref(s) in the Creation Kit.


   Hold [S + LMB Down on selection] + Mouse Move

      Modify the scale of all selected refs in the Creation Kit, with the mouse 
      movement direction serving as input (determining the increase or decrease 
      in scale).


   [B + Left Stick upward]

      Perform an upward special move in Super Smash Bros..


For the first two binds,  the vector control isn't part  of the bind itself. If 
you click  and hold on a selected ref, then you'll begin a drag-move  operation 
(or drag-scale,  if S is held) even if  you don't actually move  the mouse; any 
subsequent mouse movement is just fed to that operation as a parameter. We need 
a way to feed  scalar or vector inputs  to a bound function as  parameters, but 
any system we build  for that is orthogonal to the bind  itself i.e. orthogonal 
to actually triggering the bound function.

It's only for the third bind above that  the vector control is actually part of 
the bind: the joystick must  be pointed upward in order  for the bound function 
to trigger,  regardless of whether the joystick input is ever  fed to the bound 
function as a parameter.

== EDGE-CASES =================================================================

=== THE SAME KEY, BUT DIFFERENT PRESS TYPES ===================================

Suppose, for the sake of argument, that the timing threshold that distinguishes 
a normal press from a long press is 1.5 seconds.  Suppose also that we have the 
following input bindings, each mapped to a different function:

   Press X
   Long Press X

If the user presses the X button down for less than 1.5 seconds,  and then they 
release the button, then we should activate the "Press X" bind; whereas if they 
keep the  button down for  1.5 seconds or longer,  then we should  activate the 
"Long Press X" bind. This is all well and good. Suppose instead that all of the 
following binds exist:

   Press X
   Long Press X
   Hold X

When the user presses X, what do we do?

The behavior I've decided on is this:  in addition to a "begin long press" time 
threshold, we'll also define a "long-press  to hold-press" threshold; let's say 
that it's 1.0 seconds. This means that the user's inputs are handled like so:

   [keydown] X
    - We do not trigger the Hold X bind.

   [1.5 seconds pass]
    - The "Press X" bind is no longer eligible,  and will not activate when the 
      key is released.

   [1.0 more seconds pass]
    - We've cleared the "long-press to hold-press" threshold,  and so the "Long 
      Press X" bind is no longer eligible, and we begin continuously triggering 
      the "Hold X" bind.

   [keyup] X
    - We stop triggering the "Hold X" bind, and do not trigger the "Press X" or 
      the "Long Press X" binds.


Finally, what about the following cases:

   Bind 1: Hold X
   Bind 2: Hold [X + Y]
   
   Bind 3: Long Press A
   Bind 4: Hold A + B

   Bind 5: Press V
   Bind 6: Hold  U + V

When processing inputs,  we should activate the most specific matching bind. We 
therefore can derive the following rules for the above binds:

 - When X is pressed and held by itself,  Bind 1 activates. If Y is pressed and 
   held while X is held,  Bind 1 deactivates and Bind 2 then activates. If Y is 
   released and  X is kept held, then Bind  2 deactivates  and Bind 1 activates 
   again.

    = RULE: The most specific matching bind is the one that activates.

 - Bind 3 activates when the A key is  pressed for a certain amount of time and 
   then released, unless the B key goes down at the same time as the A key.

    = RULE: Handled by "Hold-claiming;" see below.

 - Bind 5 activates when V  is pressed and released,  unless U was the previous 
   key to be  pressed and released, and U was released recently  (we'll need to 
   define a time threshold somewhere). If U is a recent key and is the previous 
   key, then pressing V instead begins Bind 6, blocking Bind 5.

    = RULE: The most  specific matching  bind is the one  that activates. (Case 
      for non-concurrent key sequences.)


=== CONCURRENCY AND HOLD BINDS ================================================

Above, I described the "press types" as kinds of button presses; however, we're 
applying press types to  bound inputs as a whole,  which may encompass multiple 
buttons, either together or in sequence (or some combination).  We thus need to 
decide which part(s) of a bound input the press types apply to.

For example, if we implement the Konami code as a Hold bind,  then what part of 
the bind should require  that a button be  continuously held? If all buttons in 
the bind are subject to the press type, then the following ordered sequences of 
input are indistinguishable from one another:

   Up + Up + Down + Down + Left + Right + Left + Right + B + A + Start

   Up + Down + Left + Right + Left + Right + B + A + Start

After all,  when the Up key is being held down,  the Up key is being held down; 
enforcing the "Hold" press  type on each constituent button  in the bind causes 
repeated presses  of the same button to  blend together. No: the  most sensible 
rule seems to be that we  should apply the press type  to the terminal input in 
the bind.  For the bind above, you would  press those buttons in  sequence, and 
then press Start and keep it held to activate the bind continuously.

This of course means that we can't  represent button combinations which require 
a mixture of presses, long presses, or  holds. For now, those inputs are out of 
scope. I wasn't able to find any  major examples of such button combinations on 
gamepads in the wild; the  only examples I could easily  find were from various 
PlayStation dev kits, with binds such as:

   Long Press [D-Pad Left + LT + RT + Square] + Hold Start

So no -- for now, we'll have press types exist as a property of the entire bind 
while affecting only  the trailing input. But... what is  the "trailing input?" 
It seems like a reasonable definition  should be the last button in the bind... 
but suppose that we have a Hold bind defined as the following:

   A + B + [X + Y]

Here, we must press A, then B, followed by both X and Y concurrently. It stands 
to reason, then, that when a bind ends with a concurrent group of buttons, that 
entire group should be the trailing input; therefore, to activate this keybind, 
you would enter the following sequence of inputs:

   [keydown] A
   [keyup]   A
   [keydown] B
   [keyup]   B
   [keydown] X
   [keydown] Y

The bind would then remain active until either of X or Y are released, at which 
point the concurrent group as a whole is no longer down.


=== HOLD BINDS AND SEAMLESS SWITCHING =========================================

The Creation Kit  has a small family of "light/scale" keybinds,  which activate 
when  the user holds  one or more keys, and then left-clicks  and drags on  any 
selected ref in the Render Window. They are as follows (all keys are concurrent 
in each bind):


   LMB Drag

      Drag-move the selected refs around the environment.


   S + LMB Drag

      Continuously adjust  the scaling of all selected refs:  moving the cursor 
      upward or leftward increases; downward or rightward decreases.  If any of 
      the selected refs are lights, then this bind modifies their radii instead 
      of their scales.


   Alt + S + LMB Drag

      Continuously adjust the  FOV of all selected spotlight  refs. Conventions 
      for cursor movement are as described above.


   Ctrl + Alt + S + LMB Drag

      Continuously adjust the fade (brightness) of all selected light refs. The 
      conventions for cursor movement are as described above.


   Alt + B + LMB Drag

      Continuously adjust the shadow depth bias of all selected light refs. The 
      conventions for cursor movement are as described above.


The behavior of these binds is such that as long as you keep LMB held after you 
trigger any of these binds, you can press or release their various keys to swap 
between any of  them seamlessly. Consider  the following inputs,  assuming that 
LMB is initially pressed down while the cursor is over a selected ref:


   Action         | Active bind                   | Current inputs 
   ---------------+-------------------------------+----------------------------
   [keydown] S    | None                          | S
   [keydown] LMB  | Scale refs                    | S + LMB
   [keydown] Alt  | Scale FOVs                    | Alt + S + LMB
   [keyup]   Alt  | Scale refs                    | S + LMB
   [keyup]   S    | Drag-move refs                | LMB
   [keydown] B    | Drag-move refs                | B + LMB
   [keydown] Alt  | Scale shadow depth bias       | Alt + B + LMB
   [keyup]   B    | Drag-move refs                | Alt + LMB
   [keydown] S    | Scale FOVs                    | Alt + S + LMB
   [keydown] Ctrl | Scale light fade              | Ctrl + Alt + S + LMB
   [keyup]   Alt  | Scale refs                    | Ctrl + S + LMB
   [keyup]   LMB  | None                          | Ctrl + S


You can see that we can seamlessly switch between any of the above binds. There 
is another observation to be  made here as well:  note the bind that we *can't* 
trigger seamlessly. At the end of the  above input sequence, we're holding down 
the Ctrl and S keys, but we don't trigger the "save current file" hotkey.

To implement this behavior, we must track key state as follows:

 - Once any Hold bind activates, its terminal key(s) must be "Hold-claimed."
 
 - A key ceases to be "Hold-claimed" once it is released.

 - While a key is  "Hold-claimed,"  it must be  ignored by Press and Long Press 
   binds.

Consider the following binds:

   Bind 1: Hold A + [B + C]
   Bind 2: Long Press B
   Bind 3: Long Press C

In order to activate all three binds, you must enter the following inputs:


   Action         | Notes
   ---------------+------------------------------------------------------------
   [keydown] A    | 
   [keyup]   A    | 
   [keydown] B    | If we release B without pressing C, then Bind 2 will run.
   [keydown] C    | Bind 1 activates, Hold-claiming the B and C keys.
   [keyup]   C    | B is still Hold-claimed, so Bind 2 can't activate.
   [keyup]   B    | B and C are no longer Hold-claimed.
   [keydown] B    | A was not the previous press, so Bind 2 is eligible.
   [time passes]  | The "Long Press" threshold is now met.
   [keyup]   B    | Bind 2 activates.
   [keydown] C    | 
   [time passes]  | The "Long Press" threshold is now met.
   [keyup]   C    | Bind 3 activates.

   
=== MODIFIER NODES IN THE BIND TREE ===========================================

Above, we considered binds like the following:

   Hold [1 + 2]
   Hold [2]

However, we also  wish to allow  users to  define "modifier"  nodes in the bind 
tree.  This will make it easier to implement modifier keys: if you want to edit 
a modifier key, you won't have to change every single bind that uses it.

This introduces some new edge cases.
