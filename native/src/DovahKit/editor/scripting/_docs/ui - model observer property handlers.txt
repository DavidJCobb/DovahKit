
When adding rows to a table view in a Lua script, what's the most efficient way 
to configure them? If you want to set multiple properties on the new cells, how 
can you do so quickly? The naive approach would be something like this:

   for i = 1, 50 do
      my_table:append_row("Cell 1", "Cell 2", "Cell 3")
      local last_row = my_table.rows[#my_table.rows - 1]
      local cells    = last_row.cells

      cells[1].text_color = "#FF0000"
      cells[3].italics    = true
   end
   
This, however, doesn't take full advantage  of our script core's multi-threaded 
nature. Script  execution and UI write  operations can run  asynchronously from 
one another, so if a script performs several write operations in a row, without 
performing any read operations in the meantime, then the script can continue on 
without having to wait  for those write operations to  complete. This is useful 
when a script is, say, adding rows to a table based on the results of some task 
that involves a lot of processing.  However, the instant the script attempts to 
perform a UI  read operation, it must pause  and wait until all  pending writes 
are complete, and then  wait until the read is complete.  In the example above, 
the script will thus pause and wait after  each individual new row is appended, 
because we have to "read" from the UI  in order to gain access to the row after 
it is appended.

(In fact, we perform four reads in the  above sample code. The first read gives 
us access to the table's list of rows. We don't cache that in a variable, so we 
do a redundant read to access the list  again so we can use the "#" operator on 
it. The "#" operator itself is a third read, and finally, the fourth read gives 
us access to the row's list of cells.)

If we want to take full advantage of DovahKit's multi-threading, we need to set 
up our cells' properties  without performing any read  operations. Fortunately, 
the "append_row" API gives us a way to do this.

[NOTE: As of 5/5/2021 The "append_row" functionality described herein isn't yet 
implemented; this is what we're working towards.]

   for i = 1, 50 do
      my_table:append_row(
         {
            text       = "Cell 1",
            text_color = "#FF0000"
         },
         "Cell 2",
         {
            text    = "Cell 3",
            italics = true
         }
      )
   end
   
In the call above, we configure each cell in the same call we use to create it; 
we're just performing a single UI write operation. But that begs an interesting 
question about what's happening behind the scenes: we allow you to set a cell's 
text color via its "text_color" setter,  and when it's created. How do we avoid 
code duplication here? How do we use  the same code to handle the text color of 
a cell both while creating it and when working with it after its creation?


=== MODEL OBSERVER PROPERTY HANDLERS ==========================================

Model  observers are already explained in the <ui - model observers.txt>  file, 
but to recap the concept very briefly,  they are the means through which Lua is 
able to safely refer to rows, columns, and  individual items inside of a model.

A "model observer property handler," or "MOPH," consists of four core parts:

 - A property name, to expose to Lua.

 - A Qt::ItemDataRole.

 - A "push" function, which takes a QVariant extracted from a model item's data 
   and pushes that QVariant's value onto the Lua stack.
 
 - A "pull" function,  which extracts a value from the Lua  stack and stores it 
   in a QVariant, suitable for use as a model item's data.

MOPHs allow us to define common handling for model observer setters and for any 
API like (table_view:append_row)  which, as shown  above, can convert key/value 
pairs into data to be written into a newly-created model item.

The simplest example  of a MOPH would be  the "text" property  for table cells. 
This MOPH uses the name "text" and the  role Qt::ItemDataRole::DisplayRole. Its 
"push" function  receives a QVariant pulled from the model  item's DisplayRole, 
casts the QVariant to  QString, and pushes the string  content to Lua as UTF-8. 
The "pull" function receives  a string from Lua,  converts it to a QString, and 
wraps it in a QVariant.

A more complicated MOPH would be the  "text_color" property for table cells. We 
want that property to support RGB(A) arrays, tables with named RGB(A) keys, and 
any string syntax  that is accepted by  HTML and CSS. Accordingly,  this MOPH's 
"pull" function is quite a bit more complicated, having to support multiple Lua 
value types and perform all sorts of  string parsing. This is a situation where 
we benefit  from not having  to write the same code  twice, in  addition to the 
other benefits of being able to list  all of a model observer type's properties 
in one place and generate [gs]etters from them at run-time.


=== OTHER NEEDS ===============================================================

Model observer property handlers don't simply need to be able to transfer whole 
values between QVariants and Lua, however. There are quite a few cases where we 
need to work with "partial values," or rather, a value received from Lua should 
be used not to overwrite an already-existing value, but to modify it.

One of those cases is  text alignment, which can be configured  on some widgets 
and on some model items. Lua works with text alignment by way of a string which 
contains two  keywords, separated by a  space. The first keyword  specifies the 
horizontal alignment, and the second  keyword specifies the vertical alignment. 
The trick  is that  "unchanged" is an  allowed keyword.  If you set  a widget's 
alignment property to "center unchanged",  for example, the Lua API will center 
the widget's text  horizontally, but keep whatever vertical  alignment the text 
had beforehand.

In order to implement this for model  items, it isn't enough to simply transfer 
QFlags<Qt::AlignmentFlag> values between QVariants and Lua. When we actually go 
and write a QVariant into the appropriate item data role, we need to be able to 
have the MOPH perform special handling  at that time in order to smoothly merge 
the prior value with the new value.

Font properties are another example of  where this is needed. Our current plans 
are to offer discrete  font properties: booleans for  bold and italics, numbers 
for letter spacing and size, and a string for the typeface. However, within Qt, 
all of these properties are encompassed by a single object, QFont, and a single 
role, Qt::ItemDataRole::FontRole. In order to split them up as desired, we need 
to be able to offer MOPHs for each  individual Lua-side value which merge those 
values into the broader QFont.
