
DovahKit's scripting API allows Lua scripts to create UI windows and manipulate 
them, in order to  display information  and ask for input.  Naturally, however, 
this means that the script  engine needs to manage  the lifetimes of spawned UI 
widgets and objects. How is this done?

Our primary goal  is to ensure that script authors don't have  to manage native 
objects themselves. A script author should never have to manually delete any of 
the objects that we  allow them to create, nor should they  have to worry about 
memory leaks  from objects that were not explicitly deleted.  Rather, we should 
automatically delete any native objects that are no longer being used by Lua or 
Qt (and that are no longer reachable via either).

This, of course,  means that we need to properly determine  when native objects 
are reachable -- that  is, when the objects are either referred  to directly by 
Lua, or can be retrieved via some other  object that is referred to directly by 
Lua. Let's start by examining one of the more complicated cases: QWidgets.


=== LIFETIME MANAGEMENT FOR UI WIDGETS ========================================

All QObjects,  including widgets, belong  to a hierarchy,  wherein each QObject 
can have one "parent" QObject and any  number of "child" QObjects. Object types 
can mix and match,  with widgets able  to have non-widget  parents or children. 
This hierarchy is primarily an ownership  model: when deleted, a parent QObject 
will automatically delete its children.

It is possible for objects like QButtonGroup  to "bridge" widget hierarchies. A 
QButtonGroup can be used to make  multiple QRadioButtons behave in tandem, even 
when they aren't part of the same hierarchy.

We'll say that  an object is "Lua-referenced" if there exists  any Lua userdata 
that refers directly to that object  (in whole or in part). The antonym to this 
term is "Lua-unreferenced."

We shall say that a QWidget is "orphaned" if it has no parent widget.

Finally, we shall say  that a widget  hierarchy, its  contents, and its bridges 
are "abandoned"  if none of the widgets or bridges in that  hierarchy or in any 
bridged-to hierarchy are Lua-referenced,  and if none of those hierarchies have 
as their root a  visible QDialog. Visible dialog boxes should  never be deleted 
even if the script has discarded all variables that once referred to them.

With all these facts in hand, we can make a few deductions.

No matter how we  decide to handle object lifetimes, we must  explicitly delete 
all objects when the script VM is torn down -- that is, when the script is done 
running, whether because it completed or because it encountered an error or was 
force-killed by the user. This implies a need to keep track of all objects that 
we let a script  create; in practice, however, because deleting  a QObject will 
also automatically delete all of its descendant QObjects, we only need to track 
root and orphaned QWidgets, along with bridges.

(As a side note, QObjects can be deleted  from any thread via the "deleteLater" 
member function, so we could instantly delete QWidgets upon some criteria being 
met; however, it would be better to instead mark them for deletion and then run 
QObject::deleteLater  within our script  loop -- outside of  any event listener 
processing or similar -- so that we can  safely perform tasks like deleting any 
pending UI events  for the to-be-deleted object. Accordingly,  then, we need to 
maintain  two lists of QWidgets: one for  orphans and one for widgets  that are 
pending deletion.  Similarly, we need  two lists of QButtonGroups:  one for the 
QButtonGroups that are not abandoned,  and another for those that are abandoned 
and therefore pending deletion.)

Now, if we assume a lockstep threading model, wherein every action requested by 
Lua blocks  the script  thread until completed, then  by definition,  it is not 
possible for  any abandoned  widget or object  to become  Lua-referenced again; 
these are objects that  have been "lost"  by the script. This  is not, however, 
the threading  model we actually  use, but let's  ignore  that and try a simple 
approach to widget garbage collection.

The naive approach -- certainly a good starting point -- would be to design the 
VM to delete a "root" widget the very instant its hierarchy is abandoned. We're 
capable of reacting to our userdata being  garbage-collected via the __gc meta-
methods, so we can react to abandonment instantly. Now, this is a good solution 
in theory, but remember  what I said above:  our script engine  runs across two 
threads, and it does not use a lockstep threading model. In order to understand 
what that means, we need to look at an example.

   local child = ui.button.new()
   do
      local parent = ui.widget.new()
      parent:add_child(child)
   end
   collectgarbage("collect")
   collectgarbage("collect") -- has to be twice
   
In the example above,  we create a parent widget and a child  widget, and we do 
so in such a way that the parent  widget will  go out of scope before the child 
widget does. We then call Lua's built-in "collectgarbage" function to force the 
Lua VM to perform a garbage collection pass; we need two calls in order to deal 
with object  finalization (i.e. the  first call will run widget  wrappers' __gc 
metamethods and then mark the wrappers as  "finalized;" the second call is what 
actually deletes them).

You probably expect  these operations to occur one after another,  in sequence, 
but in  reality, many UI  operations are fire-and-forget  and do not  block the 
script thread, and  (widget:add_child) is one of them. What  this means for the 
example above is that events typically occur in the following order:

 - The child widget is created.

 - The parent widget is created.

 - The script thread asks  the main thread to insert the  child widget into the 
   parent widget. This will occur later, but it will not occur instantaneously.

 - The script thread  forces a garbage  collection pass.  This triggers garbage 
   collection of the userdata wrapper for the parent widget.

 - When the parent widget is garbage-collected,  we check whether it belongs to 
   an abandoned hierarchy. Of course, the parent widget is unreferenced and the 
   child widget hasn't  actually been  appended yet --  that operation is still 
   pending -- so technically, the parent  widget is a hierarchy unto itself and 
   that hierarchy contains  no referenced widgets. The  parent widget, then, is 
   abandoned, and will be marked for deletion  -- that is, it will be placed in 
   a QVector so that we can  call QObject::deleteLater on it  at an appropriate 
   time.

 - The main thread will  receive the request to append the  child widget to the 
   marked-for-deletion parent widget. Now we're headed for disaster.

 - The script thread will reach an appropriate point in its spin-loop and pause 
   to scan over all  marked-for-deletion widgets. Any pending  events for these 
   widgets will be deleted without being forwarded to Lua, and then the widgets 
   themselves will be deleted via a call to QObject::deleteLater.

   Because the parent widget was marked for deletion, it will undergo this same 
   process; and because the child widget has now been appended to it, the child 
   widget will be deleted as an indirect consequence.

What we're left with, after this situation  plays out, is a dangling pointer to 
the now-deleted child widget. If the Lua script performs any operation upon the 
"child" variable  that would result  in actually  trying to access  the wrapped 
QWidget, then the script will read bad  memory and (hopefully) crash. Obviously 
we want to prevent this. Fortunately, there's a way.

Remember that we must keep track of when  widgets become orphaned and when they 
cease to be orphaned -- when they are appended to a parent. We can leverage the 
"adoption"  detection to  fix the edge-case described  above: when  a widget is 
appended to a parent (and, by implication, to a widget hierarchy), we can check 
whether the hierarchy  root is marked for deletion and if  so, unmark it. Easy.

The functions that  actually handle all of  this, then, are  all members of the 
DovahKitScriptVMCore singleton and are:


 - _hierarchy_finder

   A utility class; given a widget, bridge,  or other hierarchy-relevant object 
   to serve as a starting point, a hierarchy  finder will traverse all widgets, 
   bridges, and hierarchy-relevant  objects reachable from that starting point. 
   The finder can optionally be configured to stop early (producing no output) 
   if it finds that the hierarchies in  question are not abandoned.


 - widget_no_longer_referenced

   Called by our userdata internals when a QWidget is no longer Lua-referenced. 
   (We'll talk about how we actually detect that situation later.) The function 
   uses a hierarchy finder to determine whether the unreferenced widget's cont-
   aining hierarchy is now abandoned, and if so, it passes the finder's results 
   to (mark_abandoned_hierarchy_for_delete).


 - mark_abandoned_hierarchy_for_delete

   Receives a hierarchy finder, and loops over the root widgets and the bridges 
   in that finder. All such objects are marked for deletion. This function also 
   helps to keep track of how many widgets the script has active.


 - unmark_rescued_hierarchy_for_delete

   Receives a hierarchy finder, and loops over the root widgets and the bridges 
   in that finder.  All such objects are  unmarked for deletion.  This function 
   also helps to keep track of how many widgets the script has active.


 - widget_no_longer_orphaned

   Called by any Lua APIs that append a  widget to a parent. Removes the widget 
   from the VM's orphan list, and  then checks whether the root of the widget's 
   containing hierarchy is marked for deletion; if so, the root is unmarked for 
   deletion and inserted back into the orphan list.


 - button_group_lost_a_member

   Called by any Lua APIs that remove a QAbstractButton from a QButtonGroup. If 
   the QButtonGroup is unreferenced, this function will behave similarly to its 
   widget counterpart,  (widget_no_longer_referenced): it will  mark the button 
   group's containing hierarchy for deletion if the hierarchy is now abandoned.


 - button_group_gained_a_member

   Called by any Lua APIs that add a  QAbstractButton to a QButtonGroup. If the 
   QButtonGroup was previously unreferenced  and had no buttons, and was marked 
   for deletion for this reason, then it will be rescued from deletion.


 - button_group_no_longer_referenced

   Called by our userdata internals when a QButtonGroup is no longer Lua-refer-
   enced. (As with widgets, we'll talk  about how we detect that situation in a 
   later section.)  Behaves pretty much identically to its  widget counterpart, 
   (widget_no_longer_referenced).


The vast majority of the above functions run on the script thread. We'll talk 
about the ramifications of this later.


=== HOW DO WE TELL WHEN SOMETHING IS LUA-UNREFERENCED? ========================

The naive approach  to detecting when an object is and isn't  Lua-referenced is 
to store a refcount somewhere. We can run code when we push a new userdata into 
Lua, and we can run code when a userdata is garbage-collected, and this is what 
we would need in order to manage a refcount.

The issue with  this approach, however, is that not all native  objects that we 
allow Lua to create will have a refcount  field. Sometimes, we might be able to 
store a refcount somewhere in the object, as in the case of QWidget properties, 
but other times, we would have to go to  the trouble of creating a wrapper type 
for the object  or engaging in other shenanigans;  and this in turn  means that 
our object lifetime management is a bit inconsistent.

Fortunately, we can take advantage of  how userdata are stored and recycled, to 
eliminate the need for a manually tracked refcount. Our scripting core stores a 
hidden table of lists of userdata --  one list per wrapped object. This storage 
is used to recycle userdata: if a Lua API  function is called twice and returns 
the same result, then it should return the same userdata, rather than returning 
two different userdata that wrap the same object (which would test as different 
objects  unless we wrote a custom `__eq` metamethod). Each of the  lists in our 
storage is a  weak-table, which means  that it's configured  not to prevent the 
garbage-collection  of its own values: if  those values  aren't in use anywhere 
else in Lua, then they'll disappear from the list.

Our userdata storage is laid out like this,  where `storage[bare_pointer]` is a 
weak-table:

   type(storage[bare_pointer][unique_key]) == "userdata"

Accordingly, we  know that a native  object is Lua-referenced  if it has a list 
within the weak-table,  and if that list is not empty.  This means that we also 
know that a native object is Lua-unreferenced  if the list is empty or entirely 
absent.

We can design our userdata `__gc` and  `__close` metamethods, then, to identify 
the list  that once contained the userdata, and check if the list is  empty. If 
so, we'll delete the  list (just to keep  things nice and  neat, and maybe even 
speed up lookups), and we'll also have an opportunity to run whatever functions 
we need to whenever the userdata-wrapped native object becomes unreferenced.


=== SO HOW ABOUT THOSE RAMIFICATIONS WE SAID WE'D TALK ABOUT? =================

Above, we focused on  determining when to delete objects based  on when they're 
Lua-referenced.  I mentioned that when we're dealing with  QWidgets, all of the 
lifetime-relevant events are reacted  to on the script thread: widgets becoming 
orphaned or adopted; QButtonGroups  gaining or losing members; and so on. These 
are situations that have no usable signals  or slots within Qt, so they have to 
be dealt with by hand:  there are functions in the script  core that need to be 
called when a Lua API does something that would change a QWidget's parentage or 
a QButtonGroup's  contents, and in practice  these functions  get called on the 
script thread.  That's very  convenient for us, because  we can only  check our 
userdata storage (and thus whether the  objects in question are Lua-referenced) 
from the script thread.

Let's describe  these events, collectively,  as changes in how  the objects are 
referred to within Qt. When an object becomes Lua-unreferenced, we have to test 
whether it is also "Qt-referenced," i.e.  whether it is connected via Qt to any 
Lua-referenced  or otherwise non-abandoned object, and if the object  is indeed 
both Lua-unreferenced  and Qt-unreferenced, then it gets  deleted. This is also 
true in reverse:  when the object becomes Qt-unreferenced,  we must check if it 
is Lua-unreferenced and if so, mark it for deletion.

When QWidgets and QButtonGroups experience changes to how they're referenced in 
Qt (herein: "Qt-reference changes"), those  changes are instigated by code that 
runs on the script thread, and that same code gives the script core a chance to 
respond  to those changes  -- and therefore, that response  takes place  on the 
script thread. However, there are other object types that react to Qt-reference 
changes automatically on whatever thread  those changes actually take place on, 
which is to say,  the client thread  (which is to say,  not the script thread). 
These object types include:

 - Canvas widget layer data

 - Lua-managed resources

Generally, these  will rely on signals  and slots, or smart  pointers, to alert 
the script  core to when  they become Qt-unreferenced;  and so when  the script 
core reacts,  that reaction  occurs on the client  thread, and  we can't safely 
search our userdata storage (i.e. Lua state which belongs to the script thread) 
to check whether these objects are also Lua-unreferenced.

The solution we  use is to have these  objects store an atomic  bool indicating 
whether they are Lua-referenced.  We handle  their becoming  Lua-(un)referenced 
similarly to QWidgets, QButtonGroups,  and friends: we run code when a userdata 
is destroyed  and our storage holds no other  userdata for the  same underlying 
object; but we have that code manage the underlying object's atomic bool.
