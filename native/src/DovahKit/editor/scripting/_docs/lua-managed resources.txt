
Here's an interesting question: how do we allow Lua scripts to work with raster 
images and use them within various parts of the UI, such that we properly track 
and garbage-collect those images once neither Lua nor the UI refer to them? You 
might think that we can handle this the  same way as with widget lifetimes, but 
there are some extra issues that come into play.

   1. Lua must be able to modify the content of a resource. We want Lua scripts 
      to be able to create  and display rasters for a  variety of purposes, and 
      we want Lua scripts to be able to  perform operations on rasters that may 
      involve modifying  them (e.g.  identifying the  dominant color  of a game 
      texture by resizing it to a single pixel and sampling the pixel's color).

   2. Resources must  be usable by model  items, not just widgets.  Model items 
      can store icons in their Qt::DecorationRole,  which means that we need to 
      somehow know when items start and  stop using a given resource. There are 
      no model signals that are suitable for this purpose.

So how, indeed, do we meet these needs?


=== THREAD-SAFE MODIFICATION OF RESOURCES =====================================

It must be possible  for Lua code to modify the content  of a resource, without 
causing issues for main-thread  UI code which  may be attempting to render that 
resource. The naive approach would be to apply a thread-lock to each individual 
resource; the problem with this approach  is that it would allow script code to 
bog down rendering.

There's also  a deeper issue at play.  We need to store rasters  as QImages, so 
that Lua can access the  image data easily. However, the  Qt library prefers to 
render UI graphics using QPixmaps, which  optimize for rendering by storing the 
image content  in a platform-dependent  way. QPixmaps cannot  be read directly, 
and QImages are slower to draw.

Double-buffering solves both of these issues. For each resource, we can store a 
QImage intended for use on the script thread, and a QPixmap intended for use on 
the main thread; we can take steps to ensure that scripted modifications to the 
QImage always  flag the resource as  "desynchronized;" and we  can have code on 
the main thread which resynchronizes those resources, with this code optionally 
throttled to, say, 60 FPS to prevent the main thread from being too beholden to 
the script thread.

The resources themselves will be stored in some registry, which will be able to 
carry out this synchronization. In practice,  resources don't have a flag which 
marks them as "desynchronized;" rather,  they are placed in a specific list, so 
that we  don't have to  walk the full resource list  to find and  resynchronize 
them.


=== USING RESOURCES WITHIN THE UI =============================================

This introduces the question of how we  even use resources within the UI in the 
first place. When Lua code modifies the content of a resource that is currently 
being displayed in the UI, the widget  displaying that resource should show the 
script's changes as soon as possible. How do we allow this to happen?

The naive approach would be to simply  have a widget use the resource's QPixmap 
directly, such that changes to the QPixmap  are forwarded to the widget, but... 
that's not how QPixmaps  (or many other Qt classes) work.  QPixmaps, along with 
QImages and similar classes, rely on  "implicit data sharing." Essentially, the 
QPixmap is  just a handle  to a set of underlying  data that may  or may not be 
shared by other handles; this is why you can allocate QPixmaps on the stack and 
pass them around by value without having to worry about memory management.

This comes with some limitations, however.  Modifying any instance of a QPixmap 
will "detach" it -- that is,  it will split that handle  off, creating a unique 
copy of the data it was previously  using, so that the changes to be made won't 
affect other QPixmaps that had previously shared the same data. This means that 
we can't simply  live-update the QPixmap we store in our  internal registry, as 
doing so will "detach" it and it will no longer be sharing data with any extant 
references out in the UI.

(This, incidentally, is true even for QPixmap::convertFromImage, though the API 
reference doesn't mention it. Documentation  states that the API "replaces this 
pixmap's data with the given image," and the operative words in there are "this 
pixmap;" the function is not meant to  affect all other pixmaps that implicitly 
share data with  "this pixmap," and indeed,  checking its source  will reveal a 
call to QPixmap::detach.)

What we need to do instead, then, is this: instead of having UI widgets rely on 
a QPixmap, we need to have them refer  to the resource itself. For model items, 
this is very simple: we can simply store  something else in Qt::DecorationRole. 
This can perhaps be some sort of pointer to  the resource, which a widget could 
theoretically use to access the resource's  QPixmap (which we can update at our 
leisure) at render time.

That begs  the question of  how we actually render  the pointer.  Given an item 
data role and a QVariant, how does Qt interpret the data and render it? Special 
classes called "delegates"  are used to perform this task.  A model view widget 
will have  a delegate  (typically  QStyledItemDelegate) with a  virtual  member 
function that is  used to initialize predefined  render  options for each model 
item. Qt allows us to  define our own  delegates (including  by subclassing the 
normal QStyledItemDelegate class),  create  instances of them, and assign those 
instances  to any model  view control  (though each control  must have  its own 
delegate instance).

This, of course, doesn't solve using  Lua-managed resources for single widgets, 
such as QToolButton. We'll circle back to that later.

There's just one thing left to take care of: we need to actually get widgets to 
live-update their renders if they use a  resource that has been resynchronized. 
It turns out that there isn't any "clean" way to do that; delegates can control 
how an item data role  is rendered when  the widget  actually decides to render 
it, but they can't force the widget to render. In practice, there's really only 
one way to do what we want: we need to gather up every single UI control in the 
entire scripted UI, and call QWidget::update on them individually.

That seems like it  should be wrong, right? If you run some  tests, you'll find 
that calling QWidget::update  on a window seems to  force all of its descendant 
widgets to repaint,  so why can't we just do that for each  scripted window? As 
it turns out, that's a platform-dependent  behavior; Qt does not guarantee that 
repainting a parent widget will repaint  its descendants. Moreover, it fails to 
account for  special cases:  QComboBox, for example,  stores its  "drawer" as a 
private  QAbstractItemView not attached to the widget hierarchy, so  repainting 
the combobox alone doesn't update the  view. The only guaranteed way to repaint 
all widgets is  to actually call  QWidget::update on all widgets,  handling any 
QComboBoxes we find as a special case.


=== TRACKING RESOURCE USAGE, EVEN FROM MODEL ITEMS ============================

Next, we need to figure out how to track  when model items start and stop using 
a Lua-managed resource. We just decided that model items should store a pointer 
to the resource, so  what if instead of  using a bare pointer,  we use a custom 
smart pointer? A typical  smart  pointer will manage  the memory of its target, 
but that's not what  we want; we just want to track how many  different systems 
within Qt are referring to a resource. More formally, we want to give resources 
an intrusive  refcount, and  design a smart pointer  class which  modifies this 
refcount (and perhaps  calls some  code when it  hits zero)  but which does not 
attempt to delete the resource when the refcount hits zero.

Our resources  are instances  of LuaManagedResource,  so let's  call our custom 
smart pointer "LuaManagedResourceHandle." We'll have model items wrap this in a 
QVariant, and we'll configure it so that  when the LuaManagedResource (LMR) has 
its refcount drop to zero, we call some code within our resource registry. This 
code can delete the resource if it is, at that time, also not referenced by Lua 
anymore.

From here on out, we may abbreviate LuaManagedResourceHandle as "LMRH."


=== BEST PRACTICES FOR SCRIPTING WITH LMRs ====================================

We may impose a cap on the total  size of all Lua-managed resources, to prevent 
a renegade Lua script from blowing DovahKit up with an out-of-memory error. One 
should be mindful of this when writing scripts. Consider the following code, in 
which (item_a) and (item_b) are Qt widgets  or model items of some sort and the 
"icon" field is a setter API which passes its input into Qt somehow:

   do
      local a = raster.new({
         width  = 50,
         height = 50,
         background_color = blue
      })
      item_a.icon = a
   end
   do
      local b = raster.new({
         width  = 50,
         height = 50,
         background_color = blue
      })
      item_b.icon = b
   end

One would expect the  (a) raster to become Lua-unreferenced  as soon as it goes 
out of scope; after all, once  it's out of scope,  nothing within Lua refers to 
it. However, garbage-collection in  Lua is not  instantaneous; it may take some 
time before the  rasters actually are  marked as Lua-unreferenced,  which means 
that they may hang around even if (item_a) and (item_b) are deleted somehow.

This can cause problems if a script is  working with very many small rasters or 
with a few large rasters; if the rasters  "live" for longer than expected, then 
they will contribute  to memory limitations for longer than  expected. To avoid 
this issue, script authors are encouraged to use to-be-closed Lua variables for 
rasters that should not survive past a given block:

   do
      local a <close> = raster.new({
         width  = 50,
         height = 50,
         background_color = blue
      })
      item_a.icon = a
   end
   do
      local b <close> = raster.new({
         width  = 50,
         height = 50,
         background_color = blue
      })
      item_b.icon = b
   end

Putting the <close> attribute on a local variable will mark it as to-be-closed. 
When a to-be-closed variable goes out of  scope, Lua will check its value for a 
__close metamethod and call any it finds. Our hardcoded wrappers are programmed 
to run teardown  code on __close and on  __gc (whichever runs  first), and that 
teardown code includes marking a wrapped  LMR as Lua-unreferenced. In the above 
code snippet, the (a)  and (b) variables will be closed as  soon as they go out 
of scope,  which in turn guarantees that those rasters will be deleted  as soon 
as everything else stops referring to them.


=== IMPLEMENTATION DETAILS ====================================================

When a script API receives a Lua-wrapped LuaManagedResource, with the intention 
of passing that  resource to some UI control via a lambda-task,  the script API 
must wrap the LuaManagedResource  in a  LuaManagedResourceHandle outside of the 
lambda body  (i.e. before  calling the lambda). This  is necessary  in order to 
guard against premature deletion of the resource. Consider this Lua script:

   do
      local r <close> = raster.new({
         width  = 50,
         height = 50,
         background_color = blue
      })
      my_dropdown_item.icon = r
   end

In the code above, the (r) variable has been marked as a to-be-closed variable; 
this means that the very instant it goes out of scope, Lua will run the value's 
__close metamethod. We've designed our wrappers so that this runs the same tear-
down code as __gc, in order to allow  script authors to ensure that Lua-managed 
resources  aren't held onto by the Lua  garbage collector for longer  than they 
need to be.

In the above code, assigning to (my_dropdown_item.icon) invokes a setter, which 
receives (my_dropdown_item) as its first argument and (r) as a second argument. 
The setter function will identify the second argument as a wrapped LMR and pull 
the LMR pointer; it will then need to  pass this pointer into some cross-thread 
task object to actually store it into the model item. Commonly, we will use the 
generic "lambda"  task object, since it takes a lambda -- nice  and convenient. 
We will have the lambda capture the LMR  pointer by value. Commonly, we'll also 
flag the lambda as non-blocking, so that script execution can continue while we 
make this change to the UI. That's where we risk falling into a trap.

Assume that this is the C-side code for our API:

   int icon(lua_State* L) {
      auto& self = get_wrapper_for_thiscall<cls>(L);
      //
      LuaManagedResource value* = nullptr;
      if (!lua_isnoneornil(L, 2)) {
         auto* arg = wrapper_from_stack<wrappers::resource::raster>(L, 2);
         luaL_argcheck(L, arg != nullptr, 2, "raster expected");
         value = arg->managed_resource;
      }
      //
      auto* observer = self.model_observer;
      auto* task     = new tasks::s2m::lambda(false);
      task->handler  = [observer, value]() mutable {
         if (auto* item = observer->item()) {
            auto wrapped = QVariant::fromValue<LuaManagedResourceHandle>(value);
            item->setData(wrapped, Qt::DecorationRole);
         }
      };
      DovahKitScriptVMUITaskConduit::get().send_message(*task);
      return 0;
   }
   
The above code is vulnerable to a race condition. We create a non-blocking task 
(as indicated by passing false to the  lambda-task constructor) and pass an LMR 
pointer by value.  We then queue the  task to run and then  return back to Lua, 
without waiting for the  task to complete, and within  our Lua code, the LMR -- 
the raster -- immediately  goes out of  scope. It's  possible for the LMR to go 
out of scope and be deleted before the task runs and wraps it in an LMRH, which 
will result in our LMRH wrapping a dangling pointer.

This is why we need to create the LuaManagedResourceHandle within the API prior 
to creating our lambda-task, and have the  LMRH be captured by value. This will 
ensure that the resource is already flagged as in use by Qt before we return to 
Lua, which will prevent its premature destruction.

Incidentally, this is also why LMRs' intrusive refcounts need to be atomic: the 
LMRHs can be created and destroyed on multiple threads, sometimes at around the 
same time. We create  LMRH #1 in the API body and copy it  into the lambda (the 
capture-by-value) to create  LMRH #2. The lambda  copies LMRH #2 into the model 
item's  Qt::DecorationRole to create LMRH  #3 on the main thread,  and then the 
lambda and LMRH #2  are destroyed on the  main thread;  meanwhile, the API body 
returns to  Lua, taking  LMRH #1 out of scope and destroying  it. All  of these 
operations after the creation of LMRH #2  are essentially unordered, and so the 
refcount must be atomic to allow thread-safe usage.

Incidentally, the model observer property handler system behaves as needed here 
because its  setter stuffs the  to-be-stored value  into a QVariant  within the 
script thread; so long as we ensure to  use an LMRH there (and we do), it works 
fine.
