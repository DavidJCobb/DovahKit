
In order to run user  scripts without them  being able to  threaten the rest of 
the program (i.e. in order to prevent  script mistakes from freezing DovahKit), 
we run Lua code  on a separate  thread. This means that we can offer the user a 
button to forcibly terminate a running script, but it also complicates the task 
of actually  implementing a script VM,  as most tasks now involve  cross-thread 
communication.

Let's set out our basic communication model:

 - The script thread  can send messages  to the main thread,  and may choose to 
   block until those messages  are acknowledged.  Messages that don't block are 
   "asynchronous;" these messages involve  minor tasks like writing messages to 
   a log panel,  where the script doesn't need to know or care  whether or when 
   the task completes.

 - The main thread  can send messages  to the  script thread,  but should never 
   block until they're  acknowledged (that'd defeat the  purpose of all this!). 
   Main-to-script messages fall into two categories: "urgent" and "normal." The 
   former are messages that directly affect  the "integrity" of script-accessed 
   data,  such as notifications  about form deletion;  the latter are  messages 
   that would trigger more  script code to run.

   As one can guess,  "urgent" messages  should be processed  ahead of "normal" 
   messages. That said, it's important to  keep our limitations in mind: urgent 
   messages cannot actively interrupt the running script.

This sort of communication model should  allow for reasonably fast scripts, but 
it also means that the two threads  can't act independently on the same data at 
the same time.  The main thread, for example,  can't delete  forms unless it is 
doing  so at the behest of the script  thread, with the script thread  blocking 
until it is told that the task is complete. In practice, this means that Dovah-
Kit has to block the entire editor UI while a script is running.


===== HOW WE IMPLEMENT SCRIPT TERMINATION =====================================

Lua offers a number of  "debug hooks" that can be used to  run native code. One 
of these hooks is the "count hook," which  runs after every few script opcodes. 
Per documentation,  the more frequently we run this,  the more of a performance 
cost it will have.

Our chosen debug hook checks a single boolean value, which indicates whether we 
want to terminate the script. If this value is (true), then the debug hook will 
throw a Lua script error. If this error  is not caught by the script itself, it 
will cause the  script to terminate cleanly:  all allocated  memory is properly 
cleared,  and because the  debug hook only runs  between Lua instructions,  the 
script shouldn't be in the middle of a  native-code API that may have resources 
locked.

The easiest way to  prevent the error from being caught by  the script would be 
to simply  withhold access  to Lua's (pcall) and  (xpcall) functions.  However, 
denying script authors all access to error handling is a *bit* extreme, so what 
we do instead is offer a handwritten  version of (pcall), designed to refuse to 
catch errors if the script has been asked to terminate early.

And thus, with  this trick and  with the script  on its own thread,  it becomes 
impossible for code like this (or something a little more accidental) to freeze 
the editor and cost the user their work:

   while true do
   end


===== WHEN ARE MESSAGES CHECKED? ==============================================

Messages sent from the script thread to the main thread are checked every tick, 
using a QTimer with a zero-millisecond interval as recommended in Qt's documen-
tation for the QEventLoop.

Messages sent  from the main  thread to the script  thread are  checked between 
script invocations. Put more clearly, they are checked:

 - After the main script body has finished running.
 
 - After any event listeners  registered by a script  finish running (and these 
   event  listeners would themselves be  triggered as a result of  checking the 
   messages sent from the main thread to the script thread).

It would theoretically be possible to check for urgent messages and act on them 
while a script is running, if we did  so during our Lua debug hook. However, it 
would be pointless.  It wouldn't  allow us to  react to changes  to Lua-wrapped 
data (e.g. the deletion of forms) occurring  in the background while the script 
runs, because  those changes  could occur while  native code is  running on the 
script  thread. This is  the reason why the main thread  should never  make any 
changes to the underlying data except  at the behest of the script thread, with 
the script thread blocking while those changes are occurring.
